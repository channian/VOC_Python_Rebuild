# B 棧測試操作手冊

> 對象：專案負責人（非本專案開發者），Windows + `cmd.exe`，Python 熟悉度中等。
> 目的：照著做就能把 B 棧（Schema B / PostgreSQL）跑起來、灌進資料、驗證功能。
> 這份文件會**邊測邊更新**：每個步驟都設計成可以獨立重跑，不必從頭來過。
>
> 相關文件：`docs/新資料建置需求.md`（環工部主表欄位定義）、`docs/本機PG測試環境.md`
> （PG 環境細節）、`docs/搬遷測試操作手冊.md`（本文件路徑一的前身，內容已併入本文件）。

## 2. 一次性準備

> 標記說明：【一次性】= 環境沒變就不用重跑；【每次】= 每次開始測試都要確認。

### 2.1【一次性】Python 套件

在專案根目錄（`VOC_Python_Rebuild\`）開 `cmd.exe`：

```
pip install -r requirements.txt
```

**預期輸出**：最後一行 `Successfully installed ...` 或 `Requirement already satisfied`。

**失敗怎麼辦**：若卡在 `psycopg2` 編譯錯誤，確認 `requirements.txt` 裡是
`psycopg2-binary`（binary 版不需要編譯器）——目前檔案裡已經是 binary 版。

---

### 2.2【一次性】準備一顆 PostgreSQL

三選一，選最符合你環境的：

**(a) Windows + Docker Desktop（最推薦）**

```
docker run -d --name voc-pg -e POSTGRES_USER=voc -e POSTGRES_PASSWORD=voc -e POSTGRES_DB=voc_b -p 5432:5432 postgres:16
```

驗證：

```
docker exec voc-pg pg_isready -U voc
```

**預期輸出**：`/var/run/postgresql:5432 - accepting connections`

> 【每次】Docker Desktop 重開機後容器可能沒自動啟動，用 `docker start voc-pg` 叫起來即可
> （資料還在，不用重灌）。若 5432 被本機其他 PG 佔用，把 `-p 5432:5432` 改成
> `-p 55432:5432`，`.env` 的連線字串 port 也要一起改。

**(b) 公司 IT 已提供 PostgreSQL**

跟 DBA 要：主機、port、資料庫名稱（空的即可）、帳密。
**程式只會建表，不會建資料庫**——空資料庫要請 DBA 先 `CREATE DATABASE`。

**(c) Linux / 沙盒（有原生 PG 16 binaries）**

```
bash scripts/dev_pg.sh
```

**預期輸出**：最後兩行印出
`[dev_pg] 完成！連線字串（供 .env 的 VOC_B_DB_URL 使用）：`
`  postgresql+psycopg2://voc:voc@localhost/voc_b`

> ⚠️【每次】`dev_pg.sh` 起的 PG **不是常駐服務**（容器重啟、閒置回收都會停掉）。
> 每次回來測試前先重跑一次 `bash scripts/dev_pg.sh`（腳本冪等，已在跑會直接略過）。
> **PG 一旦被清掉，資料也沒了，要重跑第 4 或第 5 章重新灌資料。**

---

### 2.3【一次性】`.env` 設定

專案根目錄複製 `.env.example` 為 `.env`（cmd）：

```
copy .env.example .env
```

然後用記事本打開 `.env`，確認/修改這幾行：

```
DEBUG=False
VOC_B_DB_URL=postgresql+psycopg2://voc:voc@localhost/voc_b
TEST_MODE=True
TEST_DEV_EMAIL=你的信箱@aseglobal.com
AUTH_MOCK=True
MOCK_USER_EMPNO=TEST001
MOCK_USER_NAME=測試申請人
```

| 設定 | 為什麼 |
|---|---|
| `DEBUG=False` | 🔴 **一定要關**。開著會讓 SQLAlchemy 把每一句 SQL 印到畫面上，真正的錯誤訊息會被淹沒。詳見 [FAQ #3](#faq-3畫面刷一堆-sql看不到錯誤在哪)。 |
| `VOC_B_DB_URL` | B 棧連哪一顆 PG。**Docker 方案用上面的預設值就好。** |
| `TEST_MODE=True` | 所有信改寄 `TEST_DEV_EMAIL`，不會真的發給名單上的同事。**測試期間絕對不要關。** |
| `AUTH_MOCK=True` | 不強制登入，直接進得了頁面。 |
| `MOCK_USER_EMPNO` | 你現在「扮演誰」。測簽核閉環時在申請人／簽核人之間切換（改完要重啟 `main_b.py`）。 |

> `.env` 已列在 `.gitignore`，不會被 commit。

---

### 2.4【一次性】建表

```
python -c "from database_b import create_all_b; create_all_b()"
```

**預期輸出**：沒有任何輸出（沒消息就是好消息）。

**失敗怎麼辦**：
- `could not connect to server` → PG 沒起來（回 2.2）或 `VOC_B_DB_URL` 打錯。
- `password authentication failed` → 帳密與 PG 不符。

> ⚠️ **`create_all_b()` 只會「建立不存在的表」，不會幫已存在的表補欄位。**
> 這是最容易踩的坑，務必讀完第 3 章。

直接跳到 **[第 3 章](#3-資料庫結構異動怎麼更新最容易踩的坑)**，跑一次檢查腳本。

### 2.6【一次性 / 換路徑時】清庫重來

要從「路徑二假資料」換成「路徑一真資料」（或反過來），**必須先清庫**，否則會撞唯一鍵。

把下面存成專案根目錄的 `reset_b.py`：

```python
# reset_b.py — 清空 B 棧全部資料表並重建（僅限測試庫！）
from database_b import create_all_b, drop_all_b

drop_all_b()
create_all_b()
print("B 棧資料表已全部刪除並重建（空庫）")
```

執行：

```
python reset_b.py
```

**預期輸出**：`B 棧資料表已全部刪除並重建（空庫）`

> 🔴 這會刪掉 B 棧**所有**資料。只在專用測試庫（`voc_b`）跑。
> 好處是重建出來的表一定與 `models_b.py` 完全一致，順帶解掉第 3 章的欄位落後問題。

## 3. 資料庫結構異動怎麼更新（最容易踩的坑）

### 3.1 為什麼會踩到

`create_all_b()` 底層是 SQLAlchemy 的 `metadata.create_all()`。它的設計是
**只發 `CREATE TABLE`，永遠不發 `ALTER TABLE`**——「表已經存在」就整張跳過，
即使那張表少了幾個欄位也一樣。PostgreSQL 沒有「建表順便改表」這種東西。

所以當程式碼新增了欄位（例如 2026-07-31 給 `item` 表加了 `category` 與 `is_dual_bound`），
你 `git pull` 之後再跑一次 `create_all_b()`，**看起來成功、其實什麼都沒做**，
直到打開首頁才炸：

```
sqlalchemy.exc.ProgrammingError: (psycopg2.errors.UndefinedColumn) column item.category does not exist
```

（已實測重現：把 `item.category` 拿掉後 `create_all_b()` 補不回來，`/home` 直接 500。）

### 3.2 判斷方法：檢查腳本

**專案已內建這支腳本**（`scripts/check_schema_b.py`），不必自己建檔，直接執行：

```
python scripts/check_schema_b.py
```


**一切正常的預期輸出**：

```
連線：postgresql+psycopg2://voc:***@localhost/voc_b
模型定義 27 張表，資料庫實際 28 張表

【表】全部齊全 ✓

【欄位】全部齊全 ✓
```

> 「資料庫實際」比「模型定義」多一兩張是正常的——測試過程可能建過 `VOC_SCADA_WEB`
> 之類的相容表。**只有「缺少」才是問題。**

**有問題的輸出長這樣**：

```
【欄位】
【缺少的欄位】（create_all_b() 不會補！必須手動 ALTER TABLE，見手冊 3.3）：
  - item.category    型別：VARCHAR(20)
  - item.is_dual_bound    型別：BOOLEAN
```

**什麼時候要跑**：每次 `git pull` 之後、以及任何「首頁一開就 SQL 錯誤」的時候。

### 3.3 修補方法：ALTER 腳本

**專案已內建這支腳本**（`scripts/fix_schema_b.py`，冪等、可重複執行）。
日後每次 `models_b.py` 新增欄位，我們會在該檔的 `ALTERS` 清單加一行，你只要重跑一次即可，不需要自己對照 commit 記錄。

執行：

```
python scripts/fix_schema_b.py
python scripts/check_schema_b.py
```


**預期輸出**：

```
OK: ALTER TABLE item ADD COLUMN IF NOT EXISTS category VARCHAR(20)
OK: ALTER TABLE item ADD COLUMN IF NOT EXISTS is_dual_bound BOOLEAN
完成（本腳本冪等，可重複執行）
```

接著 `scripts/check_schema_b.py` 應該回到「【欄位】全部齊全 ✓」。（已實測：連跑兩次不報錯。）

> **兩個關鍵細節**（都是實際踩過的）：
> 1. 連線變數叫 **`b_engine`**。寫 `from database_b import engine_b` 會得到
>    `ImportError: cannot import name 'engine_b'`。
> 2. 一定要用 **`b_engine.begin()`**（自動 commit）。用 `b_engine.connect()` 的話
>    SQLAlchemy 2.0 預設不會 commit，跑完看起來成功、DB 其實沒變。

### 3.4 本次已知的欄位異動清單

| 表 | 欄位 | 型別 | 說明 |
|---|---|---|---|
| `item` | `category` | `VARCHAR(20)` | 項目類型：`水質` / `空汙` / `雨水溝`。2026-07-31 新增。 |
| `item` | `is_dual_bound` | `BOOLEAN` | 規格型態：`true`=雙邊（`6-9`）／`false`=單邊（`100`）／`NULL`=未指定。2026-07-31 新增。 |

另外：**`spec.tagname` 已從模型移除**（2026-07-31，tag 名稱統一以 `tag_mapping` 為唯一權威）。
舊資料庫裡若還留著那個欄位**不必刪、留著無害**——程式已經完全不讀它。

### 3.5 什麼時候用「清庫重建」比較快

如果你的資料本來就是可以重灌的（假資料、或搬遷可以重跑），
**直接跑 [2.6 的 `reset_b.py`](#26-清庫重來一次性--換路徑時) 再重灌資料，比一條條 ALTER 更省事、也不會漏**。
`ALTER` 的價值在於「已經有不想丟的資料」時。

## 4. 路徑一：轉拋現有廠棟資料（A→B）

> 目標：把 A 棧 MSSQL 的真實資料搬進 B 棧 PostgreSQL，舊服務與 B 棧**並存**對照。

### 4.1 全景圖（三段式）

```
【公司、連得到 MSSQL 的機器】
   scripts/export_mssql.py  ──►  export\*.json（12 個檔）
                                      │  複製過去（隨身碟 / 網路磁碟）
                                      ▼
【連得到 PostgreSQL 的機器（也可以是同一台）】
   scripts/migrate_a_to_b.py  ──►  B 棧 PostgreSQL
```

**為什麼要拆兩段**：匯出那一段一定要有 MSSQL 連線與 ODBC driver；
轉換載入那一段只吃 JSON，任何有 Python + PG 的機器都能跑（也方便重跑除錯）。
若你的機器同時連得到兩邊，就兩支接著跑，不用真的複製檔案。

### 4.2 步驟 1【每次要更新資料時重跑】匯出 A 棧

在**公司、連得到 MSSQL** 的機器上：

```
python scripts/export_mssql.py --db "mssql+pyodbc://帳號:密碼@資料庫IP/VOC?driver=ODBC+Driver+17+for+SQL+Server" --out export --plants K7
```

參數（**這三個就是全部**）：

| 參數 | 預設 | 說明 |
|---|---|---|
| `--db` | 讀環境變數 `VOC_DB_URL` | A 棧 MSSQL 連線字串 |
| `--out` | `export` | 輸出資料夾 |
| `--plants` | 空（＝全廠） | 只匯出這些廠區，逗號分隔 `plantno`，例 `K7,K8` |

> 🔴 **`--db` 請直接明寫，不要以為 `.env` 會生效。**
> `export_mssql.py` 是用 `os.environ.get("VOC_DB_URL")` 讀環境變數，
> 而 `.env` 裡的鍵叫 `DB_VOC_URL`（名稱不同），而且 `.env` 的值也不會被寫進系統環境變數。
> 不給 `--db` 會直接看到：
> `error: 未提供資料庫連線字串（--db 或環境變數 VOC_DB_URL）`
>
> 想省事的話，在同一個 cmd 視窗先設一次也可以（只對這個視窗有效）：
> ```
> set VOC_DB_URL=mssql+pyodbc://帳號:密碼@資料庫IP/VOC?driver=ODBC+Driver+17+for+SQL+Server
> python scripts/export_mssql.py --out export --plants K7
> ```
> 連線字串含空白或 `&` 時，`--db` 的值一定要用**雙引號**包起來。

**預期輸出**（逐表一行）：

```
  匯出 VOC_source: 3 筆 （全表）
  匯出 VOC_item: 42 筆 （全表）
  匯出 VOC_plant: 30 筆 （全表）
  匯出 VOC_dept: 12 筆 （全表）
  匯出 VOC_Mail_Type: 8 筆 （全表）
  匯出 sys_aclrole: 12 筆 （全表）
  匯出 sys_aclrolerights: 30 筆 （全表）
  匯出 VOC_SPEC: 25 筆 （過濾廠區 ['K7']）
  匯出 VOC_SCADA_WEB: 25 筆 （過濾廠區 ['K7']）
  匯出 VOC_Curve: 3 筆 （過濾廠區 ['K7']）
  匯出 VOC_closectl: 4 筆 （過濾廠區 ['K7']）
  匯出 VOC_closectl_list: 9 筆 （過濾廠區 ['K7']）
完成，共 203 筆，輸出至 export/
```

**注意事項**：
- **設定類的表一律全表匯出**，不受 `--plants` 影響（`VOC_source` / `VOC_item` /
  `VOC_plant` / `VOC_dept` / `VOC_Mail_Type` / `sys_aclrole` / `sys_aclrolerights`）。
  廠區過濾只作用在 `VOC_SPEC` / `VOC_SCADA_WEB` / `VOC_Curve` / `VOC_closectl` /
  `VOC_closectl_list` 五張。
- **看到 `⚠ 匯出 XXX 失敗：...`**：單表失敗不會中斷其餘表，但那張表會是空的。
  常見原因是 `VOC_dept` / `VOC_Curve` 的欄位名與程式假設不同——把
  `export\VOC_dept.json` 裡任意一列貼給開發端即可校正對映。
- **`VOC_SCADA_HIST`（歷史讀值）不在匯出範圍**，所以搬完 B 棧的歷史曲線頁會是空的（正常）。

把整個 `export\` 資料夾複製到要跑載入的機器上。

### 4.3 步驟 2【一次性】準備人員綁定檔

搬遷**不會把 A 棧的真人搬進 B**（避免測試信寄到不相干的人）。
所有申請人 / 簽核人 / 派送名單都改綁你指定的同事。

```
copy scripts\migration_personnel.json.example scripts\migration_personnel.json
```

用記事本打開 `scripts\migration_personnel.json`，改成你部門的同事：

```json

### 4.5 `plant_filter`（`--plants`）到底影響什麼

這點容易誤會，寫清楚：

| 對象 | `--plants` 有作用嗎 |
|---|---|
| `export_mssql.py` 匯出的 `VOC_SPEC` / `VOC_SCADA_WEB` / `VOC_Curve` / `VOC_closectl(_list)` | ✅ 有，只匯出指定廠區 |
| `export_mssql.py` 匯出的設定類表（`VOC_plant`/`VOC_item`/…） | ❌ 沒有，一律全表 |
| `migrate_a_to_b.py` 載入的 `plant` 主檔 | ❌ **沒有，一律全部載入**（廠區主檔是設定，過濾的正確場合在匯出階段） |
| `migrate_a_to_b.py` 產生的 `mail_list`（派送名單）/ `acl_user_role`（權限） | ✅ 有，只掛在指定廠區上 |

**實務建議**：**兩支都給同一組 `--plants`**（例如都給 `K7`），
語意最清楚：只搬 K7 的規格/讀值/隔離，只把同事的名單與權限掛在 K7。

**想改測別的廠**：重跑 4.2（換 `--plants`）＋ 4.4 即可，不必清庫。

### 4.6 冪等性（可以放心重跑）

`migrate_a_to_b.py` 用「以主鍵 merge」的方式寫入：存在就更新、不存在才新增。
**同一份 `export\` 連跑兩次，第二次的筆數會完全一樣，不會產生重複列。**（已實測。）

因此它可以直接掛 Windows 工作排程器當「定時轉拋 Job」，長時間跑兩邊比對。

**但有一個前提**：庫裡不能有「同名但不同 id」的舊資料——這正是為什麼
**不要把路徑一與路徑二灌進同一個庫**。詳見 [FAQ #5](#faq-5duplicate-key-value-violates-unique-constraint-item_item_key)。

| 沒帶進來的 | 影響 | 要測的話怎麼補 |

| **`tag_mapping`（0 筆）** | **同步 worker 跑起來什麼都不做**（沒有 tag 要撈） | 見 [6.1](#61-tagname--tag_mapping同步-job-靠它決定要撈哪些-tag)，用 `/ui/basedata` 的「Tag 對應」分頁手動新增 |
| **`item.category` / `item.is_dual_bound`（都是 NULL）** | 程式退回舊的「猜項目名稱」邏輯：非 `VOC` 開頭的空汙項目會被當水質、非 pH 名稱的雙邊項目（如溫度）改不動門檻 | 見 [6.2](#62-item-主檔category-與-is_dual_bound)，用 `/ui/basedata` 的「項目」分頁補，或用 `load_user_data.py` 灌 |

| **簽核流程（`flow_id` 一律清空）** | 搬進來的隔離單沒有進行中的簽核 | 正常，上線後會重新走簽核。要測簽核就在 B 棧重新送一張單 |
| **`rain_24h`（24 小時累積雨量）** | 雨水溝預警頁沒有真實雨量 | 見[第 7 章](#7-雨水溝與-24-小時累積雨量rain_24h現階段請用假資料)——**現階段請用假資料測** |
| **已刪除 / 已過期的隔離單** | 只搬「現行有效」的 | 這是設計行為 |
| **`spec.status != 1`（停用中）的規格** | 只搬啟用中的 | 這是設計行為 |

### 4.9 舊服務與 B 棧並存的注意事項

要並存對照，B 棧改用別的 port 啟動：

```

```

- A 棧：<http://localhost:8000/home>
- B 棧：<http://localhost:8001/home>

兩邊是**完全獨立的資料庫**（A→MSSQL、B→PostgreSQL），
在 B 棧做任何操作都不會影響 A 棧的正式資料。

**輸出分兩段，意思不同**：

**特性**：
- ✅ **冪等**：以業務鍵（`plant_no` / `item` / `(plant_no,item)` / `(source_table,tagname)`）
  查找後 upsert，同一份檔重跑不會產生重複列。
- ✅ **不清庫**（與 `seed_demo_data.py` 相反）——它是「疊加/更新」，
  所以可以先跑 `seed_demo_data.py` 再用它覆蓋部分資料。
- ✅ 會自己補齊 `source` 目錄表（1=SCADA / 2=CWMS / 3=QA），對著空庫直接跑也可以。
- ⚠️ **它不建人員 / 派送名單 / 隔離單**。要測簽核與派報，人員得靠
  `seed_demo_data.py` 或 `/ui/maillist`、`/ui/acl` 頁面補。

| **有燈號全情境** | ✅ 紅/橙/黃/綠/N.D/斷訊/建置中/保養中 | ❌ 看你填什麼 |
| **有歷史曲線資料** | ✅ 過去 7 天每小時一筆 | ❌ 沒有 |
| **有人員/名單/隔離單** | ✅ | ❌ |
| **有 `tag_mapping`** | ✅ 2 筆（K71.PH1.PV / K72.VOC1.PV） | ✅ 主表「Tag名稱」有填且來源=SCADA 的那些 |
| **會填 `item.category` / `is_dual_bound`** | ❌ 不填（demo 靠名稱推測即可） | ✅ **會**（從「類型」「規格型態」兩欄） |
| **典型用法** | 第一次測、想看畫面 | 上線前驗收資料 |

> **推薦組合**：先 `seed_demo_data.py` 建好人員/名單/系統設定的底，
> 再 `load_user_data.py` 把真實基礎資料疊上去。
> （但要注意項目名撞號時的處理——`load_user_data.py` 會沿用既有 `item_id`，不會出事。）

### 5.4 `seed_test_data.py` 是什麼（人工測試不用跑）

那支是給 `tests_integration/` 自動化測試用的最小資料集（廠區 `TEST1`、三個項目）。
人工測試請用 `seed_demo_data.py`，內容豐富得多。

## 6. 兩條路徑都要懂的共通主題

### 6.1 `tagname` / `tag_mapping`（同步 JOB 靠它決定要撈哪些 tag）

**一句話**：`tag_mapping` 是「A 端某張表的某個 tag → B 端某個廠區的某個項目的某個欄位」
的對照表，**同步 JOB 完全靠它驅動**。沒有 `tag_mapping`，同步 worker 跑起來什麼都不會做。

> 🔴 **`spec.tagname` 已於 2026-07-31 從模型移除，`tag_mapping` 是唯一權威。**
> 舊系統把 tag 名稱存在 `spec.tagname`，但同步 JOB 從來不讀它——改了不會生效，
> 是純粹的誤導，所以整個拿掉了。**現在只有一個地方要維護 tag 名稱。**

**欄位**（`models_b.TagMapping`）：

| 欄位 | 說明 |
|---|---|
| `source_table` | A 端來源表名。測試期一律填 **`kepware_sim`**（B 棧內建的模擬 A 端表） |
| `tagname` | A 端 tag 名稱，例 `K7.COD.PV` |
| `plant_no` | 對應到 B 棧哪個廠區，例 `K7` |
| `item` | 對應到 B 棧哪個項目（**填項目原名，不是顯示名**），例 `COD` |
| `target_field` | 寫進 `reading_current` 的哪一欄。預設 **`value`**（讀值本身）；也可以是 SCADA 自設管制值六欄之一：`scada_oos_high` / `scada_oos_low` / `scada_ooc_high` / `scada_ooc_low` / `scada_alert_high` / `scada_alert_low` |
| `enabled` | `true` 才會被同步 JOB 撈 |
| `remark` | 備註 |

`(source_table, tagname)` 是**唯一鍵**——同一張來源表的同一個 tag 只能對到一個目的地。

**三種設定方式**：

1. **網頁**（最方便）：`/ui/basedata` → 「Tag 對應」分頁 → 新增/修改/刪除。
2. **主表**：`load_user_data.py` 從主表的「Tag名稱」欄自動產生
   （**只有「資料來源=SCADA」且「Tag名稱」有填**的列才會產生，`target_field` 固定 `value`）。
3. **搬遷**：❌ **不產生**。路徑一搬完 `tag_mapping` 是 0 筆，要自己補。

**怎麼確認設對了**：跑一輪同步 worker（見 [6.6](#66-同步-worker-與派報-worker)），
看 log 的 `synced` 數字有沒有跳。若 `skipped` 很高，代表 `kepware_sim` 裡沒有那個 tag 的資料。

> **為什麼要有這張表**：舊 JOB 是「按順序逐筆比對 tag 名稱」，一旦順序或名稱有一絲落差
> 就**靜默跳過不報錯**（pH tag 改名後讀值變空白就是這樣來的）。新版改成明確對照，
> 對不到會計入 `skipped` / `errors`，不會默默漏掉。

### 6.2 `item` 主檔：`category` 與 `is_dual_bound`

`item` 是**全系統共用的項目主檔**（不是每個廠區各一份）。同一個項目名在不同廠區共用同一列。

| 欄位 | 型別 | 意義 | 怎麼填 |
|---|---|---|---|
| `item` | 字串 | **項目原名**，全系統唯一，各表 JOIN 用的鍵。例 `pH1`、`COD2` | 命名依「量測點類型」決定，**不是依廠區**。放流池 pH 一律 `pH1`、原水池 pH 一律 `pH`。同一廠有兩個量測點就填成兩列不同名稱 |
| `display_name` | 字串 | 儀表板顯示用的別名。例 `pH1` → 顯示 `pH` | 主表「顯示名」欄；留空＝顯示原名 |
| `unit` | 字串 | 單位 | 主表「單位」欄 |
| `is_active` | 布林 | 是否啟用 | 預設 `true` |
| **`category`** | `VARCHAR(20)` | **項目類型：`水質` / `空汙` / `雨水溝`** | 主表「類型」欄（**必填**） |
| **`is_dual_bound`** | `BOOLEAN` | **規格型態：`true`=雙邊 / `false`=單邊 / `NULL`=未指定** | 主表「規格型態」欄 |

**`category` 為什麼重要**：
派報信要分「水」還是「空」、簽核要找「水保養中」還是「空保養中」的簽核人、
儀表板要不要顯示雨量欄——這些原本是靠**項目名稱字串比對**（`"VOC" in item`、
`"雨水溝" in item`）判斷的。**新廠若有一個不叫 VOC 的空汙項目，就會被誤判成水質**，
連帶找錯簽核人、派報分錯類。填了 `category` 就是資料驅動，不再猜名稱。

**`is_dual_bound` 為什麼重要**：
門檻要填單一數字（`100`）還是區間（`6-9`），原本也是猜名稱——而且只認得 pH。
**溫度（如 K21 的 `20-35`）也是雙邊規格，名稱裡沒有 pH 字樣，一定被猜成單邊**，
環工部填 `20-35` 會被打回「必須為單邊規格」，等於溫度項目根本建不起來。
填了 `is_dual_bound=true` 就不會有這個問題。

**填法**：
- **`load_user_data.py`**：主表填「類型」「規格型態」兩欄 → 自動寫入。
- **網頁**：`/ui/basedata` → 「項目」分頁 → 每個項目都有「類型」「規格型態」下拉。
- **搬遷（路徑一）**：❌ 兩欄都是 `NULL`（A 端沒有這些資訊）。要測會受影響的功能就得手動補。

**留空（`NULL`）會怎樣**：程式退回舊的「猜名稱」邏輯。
`load_user_data.py` 若靠猜猜成雙邊，會印一行 `⚠ 警告` 提醒你明確填寫；
猜成單邊則不警告（因為單邊佔絕大多數，每列都警告會變噪音）。

### 6.3 `spec` 門檻（OOS / OOC / Alert / 允收值）

**四道門檻，由寬到窄**：

```
OOS（紅燈）  ← 最嚴重，超出規格
  OOC（橙燈）
    Alert（黃燈） ← 最先觸發，範圍最窄
允收值：讀值超過就亮黃燈（獨立的一條規則）
```

**燈號怎麼算**（`services/dashboard_service._calculate_light()`）：

```
斷訊 / 保養中 / 讀值是非數字文字   → '-'（灰）
讀值 >= OOS                        → 'R'（紅）
OOC <= 讀值 < OOS                  → 'O'（橙）
SCADA/CWMS 管制值 ≠ SPEC 設定值    → 'O'（橙）← 設定不同步提醒
Alert < 讀值 < OOC                 → 'Y'（黃）
讀值 > 允收值                      → 'Y'（黃）
其他                               → 'G'（綠）
```

**單邊 vs 雙邊格式**：

| | 填法 | 例 |
|---|---|---|
| **單邊**（絕大多數水質/空汙項目） | 一個數字 | `100`、`6.5` |
| **雙邊**（pH、溫度） | `低-高` | `6-9`、`20-35` |

規則：
- 每一段只能是**數字**，小數點後**最多兩位**。（`100.123` 會被擋）
- 雙邊的**下限不可大於等於上限**。（`9-6` 會被擋）
- 單邊項目填成 `低-高`、雙邊項目填成單一數字，**都會被擋**。
- 單/雙邊由 `item.is_dual_bound` 決定（見 6.2）。
- 「尚未建置」的項目：**整排門檻留空即可**（畫面會顯示建置中），這是合法的。
  也可以明確填 `建置中`。

**⚠️ Alert 可以與 OOC 貼齊**：
有些廠區的內控標準不留黃燈緩衝，Alert 直接等於 OOC——**這是合法設定，程式允許**。
（讀值同時碰到 Alert 與 OOC 時一律亮 **OOC 的橙燈**，橙優先於黃。）

**但 Alert 不可比 OOC「寬」**：
單邊：Alert 數值大於 OOC；雙邊：Alert 區間超出 OOC 區間。
這種填法會讓「`Alert < 讀值 < OOC`」變成空區間，**Alert 永遠不會觸發**，所以程式會**擋下**，
訊息類似：`單邊規格中，OOC 上限值不可小於 Alert（可相等）！`

**⚠️ 門檻階梯要填完整，否則會出警告**：

| 你填了 | 但沒填 | 後果 | 載入器行為 |
|---|---|---|---|
| OOC | OOS | **橙燈永遠不會亮**（橙燈條件是 `OOC ≦ 讀值 < OOS`，缺 OOS 整個條件不成立） | 印 `⚠ 警告`，資料照樣寫入 |
| Alert | OOC | **黃燈永遠不會亮**（黃燈條件是 `Alert < 讀值 < OOC`） | 印 `⚠ 警告`，資料照樣寫入 |

**為什麼是警告不是錯誤**：「尚在建置中」的項目整排留空是合法的，只有「填一半」才可疑。
硬擋會讓合法資料載不進來。**看到警告請確認是不是漏填。**

**B 棧資料庫實際存法**：每道門檻在 `spec` 表拆成三欄——
`oos_low` / `oos_high` / `oos_status`（`ooc_*` / `alert_*` / `recv_*` 同理）。
`status` 是 `valid`（有效）/ `na`（無效，對應舊的 `-` / `N/A`）/ `building`（建置中）。
燈號比對**一律取上界**（`*_high`）。

**改門檻的方式**：
- 網頁：`/ui/spec`（規格維護，走簽核流程）。
- 批次：重跑 `load_user_data.py`（冪等，會更新既有列）。

### 6.6 同步 worker 與派報 worker

**兩支是獨立的 worker，責任不同，各開一個 cmd 視窗常駐跑。**

| | `run_sync_worker.py` | `run_dispatch_worker.py` |
|---|---|---|
| 做什麼 | Kepware（A 端）→ `reading_current`；順便跑斷訊看門狗 | 讀 `reading_current` 判斷異常 → 寄派報信 + 寫派報紀錄 |
| 間隔 | `system_config['sync_interval_minutes']`，預設 **5** 分 | `system_config['dispatch_interval_minutes']`，預設 **15** 分 |
| 靠什麼驅動 | **`tag_mapping`**（沒設就什麼都不做） | `reading_current` + `spec` + `mail_list` |
| 路徑一（搬遷）要跑嗎 | ❌ **不用**（讀值已經從 A 搬進來了，而且 `tag_mapping` 是空的） | ✅ 要，測派報就得跑 |
| 路徑二（假資料）要跑嗎 | 想測同步邏輯才跑 | ✅ 要 |

**同步 worker**：

```
python scripts/run_sync_worker.py
```

**預期輸出**（每一輪一組）：

```
2026-08-02 10:00:00 [INFO] run_sync_worker: 同步 JOB worker 啟動（按 Ctrl+C 可優雅結束）
2026-08-02 10:00:01 [INFO] run_sync_worker: run_sync 完成：synced=2 skipped=0 stale=0 errors=0
2026-08-02 10:00:01 [INFO] run_sync_worker: check_staleness 完成：本輪新標記斷訊=0、本輪恢復正常=0
2026-08-02 10:00:01 [INFO] run_sync_worker: 本輪耗時 0.3 秒，等待 300 秒後進入下一輪...
```

怎麼判讀：
- `synced=0 skipped=0` → **`tag_mapping` 是空的**，去 [6.1](#61-tagname--tag_mapping同步-job-靠它決定要撈哪些-tag) 設定。
- `skipped` 很高 → `tag_mapping` 有設，但 A 端（`kepware_sim`）沒有那些 tag 的資料；
  或者同一個時間點已經同步過（重跑會全部落在 `skipped`，這是正常的冪等行為）。
- `errors>0` → 下一行 `同步錯誤：...` 會說明哪個 tag 出錯（最常見是對到不存在的
  `plant_no`/`item`，撞 FK）。單一 tag 出錯**不會**拖垮其餘 tag。

**派報 worker**：

```
python scripts/run_dispatch_worker.py
```

**預期輸出**：

```
2026-08-02 10:00:00 [INFO] run_dispatch_worker: 派報 JOB worker 啟動（按 Ctrl+C 可優雅結束）
2026-08-02 10:00:03 [INFO] run_dispatch_worker: run_dispatch_b 完成：{'sent': ['K71'], 'skipped_no_recipient': [], 'no_anomaly_plants': 2}
2026-08-02 10:00:03 [INFO] run_dispatch_worker: 本輪耗時 2.6 秒，等待 900 秒後進入下一輪...
```

怎麼判讀：
- `sent: ['K71']` → 有寄出 K71 的異常信（`TEST_MODE=True` 時會寄到你的 `TEST_DEV_EMAIL`）。
- `skipped_no_recipient: ['K71']` → 有異常但**名單裡沒人**，去 `/ui/maillist` 補。
- `no_anomaly_plants: 3` → 三個廠區都沒異常（正常，代表燈號全綠）。
- **卡住不動沒有任何輸出** → 看 [FAQ #4](#faq-4派報-worker-啟動後卡住沒反應)（99% 是 SMTP 連不到）。

**兩支 worker 都是**：
- 啟動時**立刻先跑一輪**，之後才進入等待。所以「想立刻看結果」就重啟 worker。
- 按 `Ctrl+C` 會**優雅結束**（把目前這一輪跑完、commit 完才離開），不會寫到一半被砍。

**怎麼手動製造一次異常來測派報**：改 `reading_current.value` 讓它超過 `spec.oos_high`。
存成專案根目錄的 `make_anomaly.py`：

```python
# make_anomaly.py — 手動把某個項目的讀值改成超標，用來觸發派報
from decimal import Decimal

from sqlalchemy import select

from database_b import BSessionLocal
from models_b import ReadingCurrent

PLANT_NO = "K71"     # ← 改成你要測的廠區
ITEM = "SS"          # ← 改成你要測的項目（注意是「項目原名」，不是顯示名）
NEW_VALUE = "999"    # ← 改成一個一定超過 OOS 的數字

db = BSessionLocal()
try:
    rc = db.execute(
        select(ReadingCurrent).where(
            ReadingCurrent.plant_no == PLANT_NO, ReadingCurrent.item == ITEM
        )
    ).scalar_one_or_none()
    if rc is None:
        print(f"找不到 {PLANT_NO}/{ITEM} 的 reading_current，請確認廠區與項目原名")
    else:
        print(f"原值 {rc.value} → 改成 {NEW_VALUE}")
        rc.value = Decimal(NEW_VALUE)
        rc.status = "normal"
        rc.raw_text = NEW_VALUE
        db.commit()
        print("完成。重啟 run_dispatch_worker.py 即可立刻跑一輪。")
finally:
    db.close()
```

```
python make_anomaly.py
```

然後重啟派報 worker，就會看到 `sent: ['K71']` 並收到「【首發】」的信。
等 15 / 30 分鐘可以看到升級再發信。

> **測隔離抑制派報**：對某個項目送隔離申請 → 簽核核准 → 再把它讀值改超標
> → 該項目**不會**派報（被隔離抑制），儀表板顯示保養中。

## 8. 常見錯誤 / 疑難排解（FAQ）

### FAQ #1：我把多行 Python 貼進 cmd，結果一堆 `SyntaxError`

**症狀**：在 `cmd.exe` 貼進多行程式碼（或先打 `python` 進互動模式再貼），
出現 `SyntaxError: invalid syntax`、`IndentationError`，或只跑了第一行。

**原因**：`cmd.exe` 沒有 PowerShell / bash 的多行貼上處理，
每一行會被當成獨立指令送出；Python 互動模式對縮排與空行也很敏感。

**解法：一律存成 `.py` 檔再跑，不要貼多行。**

```
notepad myscript.py       ← 貼進去、存檔、關掉
python myscript.py
```

**本手冊裡所有多行程式碼都已經寫成「存成檔案再執行」的形式**
（`scripts/check_schema_b.py`、`scripts/fix_schema_b.py`、`reset_b.py`、`verify_b.py`、`make_anomaly.py`）。

**唯一可以直接在 cmd 打的是「單行」形式**，例如：

```
python -c "from database_b import create_all_b; create_all_b()"
```

（注意：`-c` 後面用**雙引號**，裡面不要再用雙引號；多個敘述用分號連接。）

---

### FAQ #2：一開首頁就 500，`column ... does not exist`

**症狀**：

```
sqlalchemy.exc.ProgrammingError: (psycopg2.errors.UndefinedColumn) column item.category does not exist
```

**原因**：`git pull` 之後程式碼多了新欄位，但**資料庫裡的表沒有跟著改**。
`create_all_b()` **只建不存在的表，不會幫已存在的表補欄位**。
（跑了 `create_all_b()` 以為補好了，其實什麼都沒發生。）

**解法**：
1. `python scripts/check_schema_b.py` → 看到底缺哪些欄位。
2. `python scripts/fix_schema_b.py` → 用 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 補上。
3. 或者，如果資料可以丟：`python reset_b.py` 清庫重建再重灌資料（最乾淨）。

完整說明見[第 3 章](#3-資料庫結構異動怎麼更新最容易踩的坑)。

---

### FAQ #3：畫面刷一堆 SQL，看不到錯誤在哪

**症狀**：跑任何指令都刷出成千上百行
`INFO sqlalchemy.engine.Engine SELECT ...` / `[generated in 0.00012s]`，
真正的錯誤訊息被埋在裡面找不到。

**原因**：`.env` 裡 `DEBUG=True`。
`database_b.py` 是 `create_engine(settings.VOC_B_DB_URL, echo=settings.DEBUG)`，
`DEBUG=True` 直接開啟 SQLAlchemy 的 SQL echo。

**解法（首選）**：把 `.env` 改成

```
DEBUG=False
```

改完**要重新啟動**服務 / 重跑指令才會生效。

**如果一定要開著 DEBUG（例如在追 SQL）**，這樣找錯誤：

1. **把輸出導到檔案再用記事本搜尋**：
   ```
   python main_b.py > log.txt 2>&1
   ```
   （`2>&1` 很重要，錯誤訊息走的是 stderr，不加就不會進檔案。）
2. **搜尋關鍵字**，由後往前找：`Traceback`、`Error`、`psycopg2.`、`sqlalchemy.exc.`
3. **真正的原因在最後一個 `Traceback` 區塊的最後一行**。
   格式一定是 `模組.類別: 訊息`，例如：
   ```
   sqlalchemy.exc.ProgrammingError: (psycopg2.errors.UndefinedColumn) column item.category does not exist
   ```
   前面幾十行 `File "..."` 只是呼叫路徑，不是原因。
4. SQLAlchemy 的 echo 行都以 `INFO sqlalchemy.engine.Engine` 開頭——
   **看到這個開頭就跳過**，錯誤訊息不會長這樣。

### FAQ #4：派報 worker 啟動後卡住沒反應

**症狀**：`python scripts/run_dispatch_worker.py` 印出
`派報 JOB worker 啟動（按 Ctrl+C 可優雅結束）` 之後就**再也沒有輸出**，
`Ctrl+C` 也要等很久才有反應。

**原因**：程式正在嘗試連公司內部的 SMTP 伺服器 `10.12.10.31` 寄信。
**這支連線沒有設 timeout**，所以在連不到的網路環境（在家、VPN 沒開、沙盒）
會**無限期卡住**。（已實測確認：卡在 `smtplib.SMTP` → `socket.create_connection`。）

**解法 A：在公司網路跑**（連得到 `10.12.10.31`）。這是正解，也才收得到信。

**解法 B：離開公司網路時，先全域暫停寄信**——這樣派報判斷邏輯照跑，只是不寄信。
存成 `pause_mail.py`：

```python
# pause_mail.py — 全域暫停/恢復寄信（system_config.mail_paused）
import sys

from database_b import BSessionLocal
from services_b.maillist_service import set_mail_paused

paused = "off" not in sys.argv        # 帶參數 off 就恢復寄信

db = BSessionLocal()
try:
    set_mail_paused(db, paused)
    db.commit()
    print("已暫停寄信（mail_paused=true）" if paused else "已恢復寄信（mail_paused=false）")
finally:
    db.close()
```

```
python pause_mail.py          ← 暫停（離線測試用）
python pause_mail.py off      ← 恢復（回公司要收信時）
```

暫停時派報 worker 的輸出會變成：

```
[run_dispatch_b] 廠區 K71 無收件人（TO 為空），略過此廠區信件
run_dispatch_b 完成：{'sent': [], 'skipped_no_recipient': ['K71', 'K72', 'K14B'], 'no_anomaly_plants': 0}
```

> ⚠️ **副作用**：暫停時不寄信、也**不會寫 `mail_log`**，
> 所以「異常件數查詢 / 異常原因回覆 / 異常報表」三頁仍然會是空的
> （那三頁的資料源就是派報紀錄）。要測那三頁，必須在**連得到 SMTP 的環境**跑過至少一輪派報。

### FAQ #5：`duplicate key value violates unique constraint "item_item_key"`

**症狀**：跑 `migrate_a_to_b.py` 時炸出

```
sqlalchemy.exc.IntegrityError: (psycopg2.errors.UniqueViolation) duplicate key value violates unique constraint "item_item_key"
DETAIL:  Key (item)=(pH1) already exists.
```

**原因**：資料庫裡**已經有假資料**了（例如先跑過 `seed_demo_data.py`）。
假資料的 `pH1` 用的是 `item_id=9101`，搬遷帶進來的 `pH1` 用的是 A 端原本的 `item_id=1`。
搬遷是「以主鍵（`item_id`）合併」，兩者主鍵不同會被當成兩筆各自 INSERT，
但 `item` 這一欄有唯一約束 → 撞。

**解法**：**清庫再搬**。

```
python reset_b.py
python scripts/migrate_a_to_b.py --export export --personnel scripts/migration_personnel.json --plants K7
```

**預防**：**不要把路徑一（搬遷）與路徑二（假資料）灌進同一個資料庫。**
要換路徑就先清庫。如果想長期兩邊都留，就開兩個資料庫，
測哪一邊就把 `.env` 的 `VOC_B_DB_URL` 指過去。

> 同一份 `export\` 資料重跑搬遷**不會**有這個問題（已實測，第二次筆數完全一樣）。
> 問題只出在「庫裡有來源不同的同名項目」。

### FAQ #6：`error: 未提供資料庫連線字串（--db 或環境變數 VOC_DB_URL）`

**症狀**：跑 `export_mssql.py` 立刻報這行。

**原因**：那支腳本是讀**系統環境變數** `VOC_DB_URL`，而
`.env` 裡的鍵叫 `DB_VOC_URL`（名稱不同），而且 `.env` 的值本來就不會被寫進系統環境變數。

**解法**：直接用 `--db` 明寫（見 [4.2](#42-步驟-1每次要更新資料時重跑匯出-a-棧)），
或在同一個 cmd 視窗先 `set VOC_DB_URL=...`。

---

### FAQ #7：`could not connect to server` / PG 突然連不上

**症狀**：任何指令都報 `psycopg2.OperationalError: could not connect to server`
或 `connection refused`。

**檢查順序**：

1. **PG 起來了嗎**
   - Docker：`docker ps` 看有沒有 `voc-pg`。沒有就 `docker start voc-pg`。
   - 沙盒：**重跑一次 `bash scripts/dev_pg.sh`**（那個 cluster 不是常駐服務，
     容器重啟就會停掉，這是最常見的原因）。
2. **`.env` 的 `VOC_B_DB_URL` 對嗎**：主機、port、資料庫名、帳密。
3. **port 有沒有被別的 PG 佔走**：本機另外裝過 PostgreSQL 也會佔 5432。

> ⚠️ 如果 PG 是被**整個清掉**（例如 `docker rm voc-pg`、沙盒回收），
> **資料也沒了**——要從 2.2 重建 PG，再重跑第 4 或第 5 章重灌資料。

### FAQ #8：`load_user_data.py` 沒讀到我的「廠區設定」

**症狀**：輸出裡寫「未提供廠區設定表，將依主表首次出現順序排序、一律顯示」，
但你明明有做那張表。

**原因與解法**：
- **CSV**：程式找的是**主表同一個資料夾**下、檔名**剛好是 `廠區設定.csv`** 的檔。
  範本檔名是 `廠區設定_範本.csv`，**要另存成 `廠區設定.csv`** 才會被讀到。
- **Excel**：工作表名稱必須**剛好是「廠區設定」**（主表放第一張或命名為「主表」）。

### FAQ #9：log 說寄了信，但我沒收到

**這通常是正常的**：

1. **`TEST_MODE=True` 會把所有信攔截改寄到 `TEST_DEV_EMAIL`**。
   信件主旨會加上 `[TEST MODE 攔截]`，內文開頭有一塊紅底提示「原本這封信會寄給：...」。
   **log 印的「原始收件人」是正式環境才會寄到的人，不是實際收件人。**
2. 檢查 `.env` 的 `TEST_DEV_EMAIL` 有沒有填成你自己的信箱。
3. 確認你在**公司網路**（SMTP 是內部 IP `10.12.10.31`）。
4. 檢查 `mail_paused` 有沒有被留在 `true`（見 FAQ #4）。

多半是**設計行為**，不是 bug：
