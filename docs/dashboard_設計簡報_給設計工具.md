# VOC 平台首頁儀表板 — 視覺重新設計簡報

> 目的：交給設計工具（Claude Desktop 或任何設計協作）閱讀，用來產出**不同視覺風格**的新版首頁儀表板。
> 這份文件只講「資料是什麼、規則不能改什麼、技術限制在哪」，**完全不限制版面/色系/字體怎麼設計**——
> 那部分請自由發揮。設計完成後回這個 repo，我會負責把它接回 Jinja2 模板與後端資料。
> 建立日期：2026-07-06

---

## 一、這是什麼系統（給設計者的背景）

工廠廢水/空污監測儀表板。使用者是廠務工程師，**每天會盯著這個畫面找紅燈**（超標項目），
一天可能看幾十次，所以「異常一眼就能被看到」是這個畫面唯一不能妥協的體驗目標。
其餘（版面、配色、字體、資訊密度、是否用卡片/表格/其他呈現方式）全部可以重新設計。

使用情境：桌面瀏覽器為主（廠務辦公室的電腦），不特別要求手機版，但不排斥響應式設計。

## 二、資料契約（設計必須遵守的欄位與意義）

後端每一列資料對應「某廠區的某個監測項目」，欄位如下（來源：`schemas/dashboard_schema.py`）：

| 欄位 | 型別 | 意義 |
|---|---|---|
| `plantno` | 字串 | 廠區代碼，如 `K7`、`K14B` |
| `item` | 字串 | 監測項目，如 `pH`、`COD`、`Cu`、`VOC` |
| `unit` | 字串 | 單位 |
| `law_spec` | 字串 | 法規許可值（政府核准上限，僅顯示參考） |
| `oos` / `ooc` / `alert_spec` / `recv` | 字串 | SPEC 三階文件的四道門檻（OOS 最嚴、OOC 次之、Alert 預警、recv 允收值）。**單邊存數字**（如 `"80"`），**雙邊（pH/溫度）存 `"低-高"` 字串**（如 `"6-9"`） |
| `scada_oos` / `scada_ooc` / `scada_alert` / `scada_oos_ll` / `scada_ooc_l` | 字串 | SCADA 系統自己記的管制值（用來比對是否跟 SPEC 同步） |
| `cwms_oos` / `cwms_ooc` | 字串 | CWMS 系統的管制值（另一套水質系統） |
| `rvalue_raw` | 字串 | **顯示用**的最新讀值原文，可能是數字，也可能是 `"N.D"`、`"斷訊"`、`"<0.05"`、`"保養中"` 這種文字 |
| `rvalue` | 字串 | 計算用讀值（上述特殊文字已轉數字，如 `<0.05→0`），設計端通常只需要 `rvalue_raw` |
| `broken` | 整數 | `0`=正常、`1`=斷訊、`2`=保養中/隔離中 |
| `source` | 整數 | 讀值來源：`1`=SCADA、`2`=CWMS、`3`=QA 人工手測 |
| `url` | 字串 | 歷史曲線連結（可能為空，見第五節備註） |
| `remark` | 字串 | 備註（斷訊說明等） |
| **`light_status`** | 字串 | **後端已經算好的燈號**：`"R"`紅／`"O"`橙／`"Y"`黃／`"G"`綠／`"-"`灰（無資料）。**這是整個畫面設計的核心**，見第三節 |
| `is_anomaly` | 布林 | 是否為斷訊/保養中/無資料狀態 |
| `plant_rowspan` / `show_plant` / `plant_has_red` | — | 如果設計仍用「表格＋同廠區合併儲存格」的呈現方式才需要這三個欄位；如果新設計改用卡片式分組，這三個欄位可以忽略，改由前端自己依 `plantno` 分組 |
| `rain_24h` | 字串 | 雨水溝項目的 24 小時累積雨量（目前可能是空字串，見第五節備註） |

**規模感**：目前約十幾個廠區 × 每廠十幾個監測項目，整頁大概 100～200 列資料。設計時请考慮「一眼掃過去抓到紅燈」在這個資料量下怎麼呈現最有效——可能是分廠區的區塊、可能是攤平表格加篩選、可能是儀表板卡片＋摘要列表，都可以提案。

## 三、不能變的業務規則（顏色語意）

無論新設計用什麼視覺語言（不一定要是「紅綠燈」的概念），**這五種狀態的區分必須清楚可辨識**：

| light_status | 語意 | 急迫程度 |
|---|---|---|
| `R` | 讀值 ≥ OOS（超過法規/管制上限）| **最高**——需要立刻处理 |
| `O` | 讀值介於 OOC~OOS 之間，**或** SCADA/CWMS 記錄的管制值跟 SPEC 文件對不上（代表有人改了規格卻忘了同步兩邊系統）| 高——這兩種原因不同但都用橙色，設計上可考慮是否要讓使用者分辨「數值超標」vs「設定不同步」這兩種橙燈的差異（目前系統沒有區分，但這是可以提出的改善建議） |
| `Y` | 讀值介於 Alert~OOC 之間，**或**讀值超過允收值 | 中——提醒觀察 |
| `G` | 正常 | 低 |
| `-` | 斷訊／保養中／無法解析讀值（`broken≠0` 或 `rvalue_raw` 是文字） | 這不是「異常」而是「這筆資料現在不能用」，語意上要跟 R/O/Y 明確區隔開（不要讓人誤以為是綠燈的一種或看漏） |

**用色自由，但要求**：
- 順序感要在（紅 > 橙 > 黃 > 綠 這個急迫度排序，使用者掃視時要能直覺分辨）
- 色盲友善（不能純靠紅綠色相區分，建議搭配圖示/形狀/文字）
- 「斷訊/保養中」這個灰色狀態不能長得像「正常」，設計上常見的坑是把它跟綠燈用類似的低飽和度顏色，使用者可能會漏看真正的斷訊

**額外的資料來源標示**（現有設計用底色區分，新設計可以用其他方式如小圖示/標籤）：
`source=1`（SCADA）／`source=2`（CWMS）／`source=3`（QA人工）— 讓使用者知道這個讀值是自動量測還是人工輸入的。

## 四、技術限制（設計落地時必須相容的部分）

1. **後端不重寫，只是視覺層**：`light_status` 等判斷邏輯已經算好在後端（見 `services/dashboard_service.py` 的 `_calculate_light()`），**新設計不需要、也不應該在前端重新計算燈號**——直接拿 `light_status` 欄位來決定視覺呈現即可。
2. **樣板引擎是 Jinja2**（Python 後端渲染 HTML，不是 SPA）。新設計如果要用互動元件（篩選、排序、展開/收合），優先考慮：
   - **HTMX**（專案已引入，習慣用它做局部更新而不寫一堆手動 JS/fetch）
   - 原生 `<dialog>` 元素做彈窗（**不要用 Bootstrap Modal**，專案明確禁止，因為要跟 `<dialog>` 混用會衝突）
   - 純 CSS/少量 vanilla JS 都可以，避免引入新的重型前端框架（React/Vue）除非有強烈理由
3. **現有設計系統**（`static/css/voc.css`）定義了一組 CSS variable，新設計**可以整套換掉**，但如果想沿用作為起點，這是目前的 token：
   ```css
   --voc-primary: #1A56A0;      --voc-bg-main: #f8f9fa;      --voc-text: #1e293b;
   --status-red: #dc3545;       --status-red-bg: #fff0f0;
   --status-orange: #fd7e14;    --status-orange-bg: #fff3e0;
   --status-yellow: #d97706;    --status-yellow-bg: #fffbeb;
   --status-green: #22c55e;     --status-green-bg: #f0fdf4;
   --status-gray: #94a3b8;      --status-gray-bg: #f1f5f9;
   --data-scada: #fff8dc;  /* 米白 */  --data-cwms: #ffe4b5;  /* 淺橙 */  --data-qa: #e2e8f0;  /* 淺灰 */
   字體：Inter（英數）＋ Noto Sans TC / PingFang TC（中文）＋ JetBrains Mono（數字等寬）
   ```
4. **既有的「每 15 分鐘刷新」倒數計時器**是現有功能（資料來源 JOB 每 15 分鐘更新一次），新設計若保留這個概念，倒數/刷新的呈現方式可以重新設計，但「使用者知道資料多久更新一次、現在的資料新不新鮮」這個資訊需求要保留。
5. **中文為主要語言**，畫面文字、任何新增的 UI 文案都要用**繁體中文**。
6. 頁面目前是儀表板本體＋一排功能按鈕（開啟其他 Modal：派送名單、規格維護、隔離申請、簽核…）。新設計如果重做整體版面配置，這些入口點需要有地方安放，但排列方式/視覺可以重新設計。

## 五、已知的資料缺口／不確定性（設計時請預留彈性，不要假設一定有值）

- **`rain_24h`**：目前後端（A 棧／舊架構）沒有真的算這個值，欄位存在但通常是空字串；未來（Schema B／新架構）才會補上。設計上雨水溝相關項目的呈現，請設計成「這個值可能暫時沒有」也不會讓畫面難看的樣子。
- **`url`（歷史曲線連結）**：舊系統這個功能的原始碼還沒拿到，目前只是個可能存在也可能不存在的連結。不要預設每一列都一定有歷史曲線可點。
- 兩套後端資料庫並存中（一套是舊 MSSQL、一套是重新設計中的 PostgreSQL），**但兩邊最終給前端的 `DashboardRow` 欄位形狀是一致的**（新架構那邊做了轉接層保證同源），所以設計端不用擔心資料從哪個後端來，欄位契約穩定。

## 六、可以自由發揮 / 我們想要的東西

- 版面配置、色彩系統、字體、資訊密度、卡片 vs 表格 vs 其他呈現方式、動效——全部開放
- 特別歡迎針對「100~200 列資料怎麼讓紅燈不被埋沒」提出你的方案（篩選？排序？只顯示異常/全部切換？依廠區摺疊？儀表板總覽+細節鑽取？）
- 如果想用不同的燈號視覺隱喻（不一定要圓點/色塊，可以是圖示、進度條、其他視覺元素），可以提案，只要五種狀態語意保留、色盲友善
- 交付格式：**純 HTML/CSS 靜態頁面（可用假資料）就可以**，不需要真的是 Jinja2 語法——我這邊會負責把設計稿轉成 Jinja2 模板接上真資料。如果直接提供 Jinja2 版本也歡迎，但不是必要條件。
