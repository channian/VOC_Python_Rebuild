# 給環工部：申請異動 Tag 前要知道的事

> 這份文件不談程式碼，只用白話說明「為什麼改一個 tag，畫面上一堆項目會跟著跳異常」，
> 以及申請廠區異動 tag 時該注意什麼。技術細節（給工程師看的）在 `docs/legacy_source_analysis.md`
> 「SCADA Tag 對應機制完整還原」章節。

## 一句話總結

**系統每 15 分鐘會去現場「按名字」抓一次資料，如果 tag 改名沒有同步告訴系統，
系統會卡住、停在舊資料不動，而且會連帶拖累「後面排隊」的其他項目，讓一堆看起來不相關的
監測項目一起跳橙燈、紅燈或顯示斷訊——但那些項目其實沒有真的異常，只是資料沒更新到而已。**

## 用一個比喻理解

把每個監測項目（例如 K12 的 pH）想像成一張「資料卡」，卡片上有好幾格要填：

- 「目前讀值」
- 「異常上限（OOS）」
- 「警戒上限（OOC）」
- 「提醒上限（Alert）」
- （像 pH 這種項目還多兩格：「異常下限」「警戒下限」）

每一格背後，都對應現場一個「感測器訊號的名字」（就是 tag，可以想成貼在感測器上的一張條碼標籤）。
系統每 15 分鐘會去現場**照著登記的名字**掃一輪所有標籤，把讀到的數字一個一個填回資料卡對應的格子。

**問題在於**：這個「填回去」的動作，是**照順序一個蘿蔔一個坑對**，不是「看到名字就直接精準對應」。
如果現場把某個標籤換了個新名字（例如廠區申請把感測器的訊號名稱改掉），但系統裡登記的名字
沒有跟著同步更新，這個「照順序對」的動作在改名的那個點就會**卡住、對不上**。而且一旦卡住：

- **這一輪**該站主機底下，**排在卡住點後面的所有 tag，全部都不會被更新**，
  資料卡上的格子維持上一輪的舊數字不動。
- 系統**不會主動跳出來告訴任何人**「哪個標籤對不上」——它就是安安靜靜地卡住，什麼訊息都不發。
- 舊數字跟現在的規格設定兜不起來，系統就會誤判成「異常」，亮橙燈、紅燈，或顯示「斷訊」。
- 這個狀況會**每 15 分鐘重複發生**，一直到把名字改回一致為止，不會自己好。

所以您可能會看到：明明只改了一個 tag，結果某個廠區一整排完全不相干的項目全部跳異常——
那不是真的水質出問題，是系統「卡住沒更新」被誤判。

## 例子

**例子 1：一般水質項目（例如 COD）只需要一個標籤**
COD 只有「上限」需要顧，所以只登記一個 tag（「異常上限」那一格）。您如果發現某個項目的
「下限」欄位一直是空的，**這是正常的**，不是漏設定，因為系統本來就只看上限有沒有超標。

**例子 2：pH 需要兩個標籤，系統會把兩個數字拼成一組**
pH 太高太低都不行，所以「異常上限」跟「異常下限」各自對應一個**獨立**的 tag。
系統抓到兩個數字後，會把它們拼成一個字串顯示（例如 `6.5-8.5`）。這就是您在資料庫裡
看到「一個門檻值好像是兩個 tag 組合起來」的真相——**背後真的是兩筆各自獨立的設定，
一筆管上限、一筆管下限，系統把兩者的值黏在一起顯示**。

**例子 3：改名沒同步，一片遭殃**
假設廠區把 K12 的「pH 下限」那個標籤，從舊名稱 `K12.PH.LL` 改成新名稱 `K12_PH_LOW`，
但只在現場設備上改了名字，沒有同時請 IT 把系統裡登記的名字也改成一致。結果：
- K12 的 pH 下限本身當然對不上、拿不到新資料。
- **同一台主機底下，排在 pH 下限「後面」登記的所有其他項目**，這一輪也全部拿不到新資料，
  一起卡在舊數字，一起被誤判成異常。
- 隔天、隔週，只要沒人發現去改回一致，天天都會重複發生同樣的異常。

## ⚠️ 比「改錯名字」更容易踩的雷：新名字的「排列順序」也不能亂

2026-09-14 補充。我們拿到系統最後一塊程式碼後發現，狀況比原本以為的更棘手：

系統去現場抓資料時，是**照 tag 名字的「字母順序」**把資料排好回來的（像字典一樣，A 開頭的排前面）。
但系統裡登記的那份清單，排列順序是**當初建檔的順序**，兩邊本來就是不同的排法，
一直以來能運作只是因為碰巧接近。

**這代表：就算您把名字改得完全正確、兩邊一字不差，只要新名字的「字母排序位置」跟舊名字不同，
一樣會整批對不上。**

**例子**：把 `K12_PH_LL` 改成 `K12_PH_LOW`
- 兩邊名字都改對了 ✅
- 但字母排序中，`LOW` 會排到 `LL` 的後面 ❌
- 現場回來的資料順序變了，系統清單的順序沒變 → 對不上 → 後面一整排項目跟著卡住

**實務建議**：異動 tag 時，**盡量讓新名字維持在原本的字母排序位置**（例如只改結尾、不改開頭；
或改成字母順序相近的名字），可以大幅降低踩雷機率。如果一定要大改名稱，請告知 IT
一併調整系統清單的排列順序。

另外，**K21、K26、K25、K16、K27、K18 這 6 個廠風險特別高**——它們抓資料的排序方式是「照時間先後」，
跟名字順序完全無關，等於長期靠運氣在運作，異動 tag 時要格外小心、改完務必確認。

## 申請 tag 異動時，請務必確認

1. **廠區端改 tag 名稱、新增/移除量測點時，必須同步通知 IT／系統維護人員，
   把系統裡登記的名字改成跟現場完全一致**（連大小寫、底線、空白都要一模一樣，
   差一個字元就會對不上）。
2. **新名字盡量維持原本的字母排序位置**（見上一節），大改名稱要請 IT 一併檢查排序。
3. **如果是 pH 或溫度這種需要「上限＋下限」的項目**，新增 tag 時要記得**兩個都要新增、
   兩個名字都要跟現場一致**，只改其中一個一樣會出問題。
4. **不要讓兩個不同項目登記同一個 tag 名字**（例如「預警pH」跟「pH」填了同一個）——
   系統只會認到其中一個，另一個永遠抓不到資料，還會害後面的項目一起錯位。
5. **改完之後不會有系統跳出來提醒您改對還是改錯**——請主動請 IT 人員在改完後確認一次，
   看看該廠區的項目有沒有恢復正常更新（不再停在改動當下的舊數字），而不是等使用者
   反映異常才發現。
6. 如果發現某個廠區突然一整排項目一起跳橙燈/紅燈/斷訊，**先懷疑是不是最近有 tag 異動**，
   再去現場確認水質——很多時候不是真的水質異常，是系統資料沒更新到。

## 看到畫面異常時，怎麼快速判斷是真異常還是系統卡住

| 畫面現象 | 可能原因 | 怎麼確認 |
|---|---|---|
| 一整排項目同時跳橙燈/紅燈 | 多半是 tag 異動造成整批卡住，不是真異常 | 查這些項目的「更新時間」是不是都停在同一個時間點不動了 |
| 某欄位變成一條灰色的槓（`-`） | 該 tag 訊號品質不良，且這個欄位從來沒成功寫入過 | 一樣看「更新時間」：完全沒跳＝名字/順序對不上；有跳但還是槓＝現場訊號真的不良 |
| 門檻值顯示怪怪的（例如 `-6.5`） | 上下限只抓到一半，被拼成畸形數字 | 這種狀況**一定會被誤判成異常、永久亮橙燈**，請立刻告知 IT 檢查該項目的 tag 設定 |

**特別提醒**：現場 PLC 若習慣用 `-1` 或 `0` 代表「這個門檻還沒設定」，**系統看不懂這個慣例**，
會把它當成真的門檻值處理，導致永久誤報。系統只認得 `-`、`N/A`、`建置中` 這幾種寫法代表「未設定」。

## 另一件環工部一定要知道的事：有些項目超標了也不會發信

2026-09-14 查證某廠**氨氣超過管制值、畫面亮紅燈，但完全沒有派報信**，原因如下：

系統判斷「這個項目超標了要不要發信」時，用的是一份**寫死在程式裡的項目名稱清單**——
只有名稱裡含有 `pH`、`Cu`、`Ni`、`SS`、`COD`、`VOC` 這幾個字的項目才會發信。

**注意：它看的是「項目名稱的字」，不是資料庫裡的分類。** 所以就算氨氣在系統裡已經歸類成「水」，
程式也看不到那個分類，「氨氣」這兩個字不含上述關鍵字 → **燈號照常變紅，但永遠不會發信**。

這代表：**任何名稱不含那 6 個關鍵字的監測項目（氨氣、導電度、溫度、流量……），
超標時都只會亮燈、不會派報，而且系統不會有任何提示。**

⚠️ **這件事需要環工部決策**：這是舊系統本來的設計（新的 Python 系統目前也照舊移植了同樣行為）。
如果實務上氨氣等項目超標也應該要發信通知，請告知我們，我們會把判斷方式改成
「預設全部都發、只有少數指定項目例外」，避免再有項目被默默漏掉。

## 這是舊系統的已知限制，新系統已經修正

上面說的「照順序對、對不上就整批卡住、也不會通知任何人」是**舊系統**的既有設計缺陷。
正在建置中的新系統（PostgreSQL / Schema B）已經改用「一筆一筆獨立比對」的做法，
單一 tag 對不上只會記錄成一筆待處理紀錄，**不會連累其他項目、也不會靜默吞掉**。
但在新系統正式取代舊系統之前，舊系統這個限制依然存在，異動 tag 時仍要照上面的 SOP 小心操作。

（派報白名單那一項是例外：新系統目前是**刻意忠實移植**舊行為，要等環工部決策後才會調整。）
