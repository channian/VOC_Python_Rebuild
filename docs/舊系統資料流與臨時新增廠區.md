# 舊系統（A 棧）資料流與「臨時新增廠區」注意事項

> 2026-08-02 建立。起因：重構尚未完成，但有臨時廠區必須**先在舊系統上線**，
> 且該廠**不走 iFIX Historian（IH）**。本文記錄舊系統實際的資料流，以及
> 「直接在 web 新增」到底會不會正常運作、有哪些坑。
>
> 全部依 `legacy/` 原始碼查證，每條都標出處，不憑推測。

---

## 一、舊系統的資料流（JOB → 資料庫 → 畫面）

```
VOC_SCADA_TagList        ← JOB 讀這張表，決定「要撈哪些 tag」
        ↓
iFIX Historian（10+ 台）  ← JOB 連線讀值
                            K11=IH、K22=IH2、K21=IH3、K12=IH4+IH5+IH6（3台）、
                            K24=IH7、K26=IH8、K25=IH10、K16=IH11、K27=IH15、K18=IH18
                            K11 另有 INSQL/Oracle WWT 第二來源（UpdateVOCData2()）
        ↓
VOC_SCADA_WEB            ← JOB 寫入：即時讀值 rvalue、SCADA 自設管制值、broken
        ↓
歷史表                    ← **同一輪 JOB 另外呼叫**寫入
                            InsertVOCHistValue() + Insert法遵VOC歷史讀值A5()
                            每天 00:00 另跑日平均
```

**Home.aspx（儀表板）不在這條寫入鏈上**——它只是「讀取」`VOC_SCADA_WEB` 來顯示，
不會產生資料、也不會寫回去。常見的誤解是「JOB → dashboard → 寫 web 表 → 歷史表」，
實際上是 **JOB 直接寫 `VOC_SCADA_WEB` 與歷史表，dashboard 只是後來的讀者**。

其他要點（出處：`docs/JOB確認清單.md`，皆已從原始碼確認）：

| 項目 | 內容 |
|---|---|
| 執行頻率 | `SCADA_VOC` 指令每 **15 分鐘**一輪 |
| 斷訊判斷 | Historian tag **品質碼 = 0** → 寫 `broken = 1` |
| broken 值 | `0`=正常、`1`=斷訊（JOB 寫）、`2`=保養中/隔離中（Web 寫）**兩者不可互蓋** |
| CWMS | **不走 Historian**，是 HTTP JSON API（`http://khfsijob/CWMSDataRelayAPI/...`），只涵蓋 K14B/K5/K7/K11/K22/K21 |
| 雨水溝 24H 雨量 | **不在這條鏈上**，是查詢時 JOIN `PMS.dbo.Water_WindRainHistValue`，JOB 不計算它 |
| pH 的 tag 數 | 每個 pH 項目要處理 **7 個 tag**（讀值 + 上下限管制值共 6 個） |

### ⚠️ Tag 比對是「順序比對」，對不上會靜默跳過

舊 JOB 靠 `VOC_SCADA_TagList.Name` 與 Historian 的 tagname **完全相符**做順序比對：

```csharp
while (TagsDT["Name"] != iHDT["tagname"]) iCount++;
```

名稱不符**不會報錯，只會靜默跳過**。而且因為是順序推進，
**一旦有一個 tag 對不上，後面的 tag 可能被塞進錯誤的欄位**。

這是已知會造成兩種現象的根因：
1. 某個管制值欄位變成 `NULL`（例如 pH 的 `alert_L` 空掉）。
2. 某個欄位出現**不合理的值**（例如 pH 的 alert 上限顯示 `-6.5`）——
   多半是錯位後撈到別的點位的值，不是該 tag 本身是負的。

> 補充：畫面若只顯示單一個數字（如 `-6.5`）而不是 `6.5-8.5` 這種區間，
> 代表**下限欄位是 NULL**——組字串的邏輯是「兩邊都有值才拼成 `低-高`，
> 否則只顯示有值的那一個」。所以看到單一數字＝有一邊沒進來。

新系統（B 棧）的 `tag_mapping` 就是為了解決這件事：明確的
`(source_table, tagname) → (plant_no, item, target_field)` 對應，**不靠順序**。

## 二、臨時新增廠區（不走 IH）：直接在 web 新增夠不夠？

### 結論：**不夠。**「在 web 新增」只會寫 `VOC_SPEC` 一張表。

`EditSPEC.aspx` 走簽核，核准後執行的 INSERT 只有這一句
（出處 `legacy/dbVOC.cs:1084`）：

```sql
INSERT INTO [VOC].[dbo].[VOC_SPEC]
  ([plantno],[item],[LAW],[OOS],[OOC],[alert],[source],[status],[tagname])
VALUES (@plantno,@item,@LAW,@OOS,@OOC,@alert,@sourceid,1,@tagname);
```

`@tagname` 是程式自己組的 `plantno + "_" + item`（見同處），**不是真的 tag 名稱**，
JOB 也不讀它（JOB 讀的是 `VOC_SCADA_TagList`），所以這欄在此情境無作用。

**舊系統的 web 沒有「新增廠區」與「新增項目」的頁面**——
`VOC_plant` 與 `VOC_item` 全站沒有任何 INSERT 語句（已全檔 grep 確認）。

### 儀表板的母集合決定了「什麼會顯示」

`Home.aspx` 的查詢（對應 `dbVOC.ListVOC()`）：

```sql
FROM      VOC_SPEC       S
JOIN      VOC_item       I  ON S.item    = I.item                      -- ← INNER JOIN
JOIN      VOC_plant      P  ON S.plantno = P.plantno AND P.isShow = 1  -- ← INNER JOIN
LEFT JOIN VOC_SCADA_WEB  W  ON S.plantno = W.plantno AND S.item = W.item
LEFT JOIN VOC_Curve      C  ...
LEFT JOIN VOC_EmptyCell  E  ...
```

| 表 | JOIN 型別 | 沒有資料的後果 |
|---|---|---|
| `VOC_SPEC` | 母集合 | 沒有這筆 → 整列不存在 |
| `VOC_item` | **INNER** | **項目沒建 → 該項目整列被濾掉，畫面上完全看不到** |
| `VOC_plant` | **INNER**（且 `isShow=1`）| **廠區沒建或 isShow≠1 → 整廠看不到** |
| `VOC_SCADA_WEB` | LEFT | 沒讀值仍會顯示，`rvalue` 為 NULL → **燈號灰色 `-`** |

所以**不走 IH 完全沒問題**（讀值那張是 LEFT JOIN），
但 **`VOC_plant` 與 `VOC_item` 必須手動補**，否則新增的規格值根本不會出現在畫面上。

> ⚠️ **順序上的常見誤解**：不是「先把廠區/項目建起來讓它出現在畫面上，之後再填管制值」。
> `VOC_SPEC` 是查詢的**驅動表（母集合）**——沒有 SPEC 那一列，
> 不管 `VOC_plant` / `VOC_item` / `VOC_SCADA_WEB` 建得多完整，畫面上都不會有這一行。
> 正確的認知是：**四張表都齊了才會出現**。

### 燈號的判斷依據是 `VOC_SCADA_WEB`，不是 TagList

`legacy/Home.aspx.cs:614` 把整段燈號邏輯包在這個條件裡：

```csharp
if (Cells[8].Text != "" || Cells[9].Text != "" || Cells[10].Text != "" ||
    Cells[11].Text != "" || Cells[12].Text != "" || Cells[13].Text != "")
{
    // 紅燈條件：最新讀值>=OOS
    // 橘燈條件：OOC<=最新讀值<OOS 或 SCADA與CWMS之管制值<>SPEC
    // 黃燈條件：Alert<最新讀值<OOC 或 最新讀值＞允收值
    // 綠燈條件：正常狀態
```

那六格是：SCADA 三個管制值（8/9/10）、CWMS 兩個管制值（11/12）、**即時讀值**（13）。
**六格全空 → 整段燈號邏輯不執行 → 維持預設的反灰。**

因此精確地說：

- **`VOC_SCADA_TagList` 只決定「JOB 會不會去寫 `VOC_SCADA_WEB`」**，它本身不參與燈號判斷。
- **真正決定亮不亮燈的，是 `VOC_SCADA_WEB` 有沒有值。**

**對「不走 IH 的臨時廠區」的意義**：TagList 沒有對應 tag **不代表永遠反灰**——
只要 QA 手測值把 `rvalue` 寫進 `VOC_SCADA_WEB`，燈號就會依 SPEC 門檻正常計算。

> 另註：即時值那一格的底色依 `source` 決定（`Home.aspx.cs:607-612`）——
> SCADA=米黃(Cornsilk)、CWMS=橘(Orange)、**QA=淺灰(LightGray)**。
> QA 來源的格子底色本來就是淺灰，與「沒有資料的反灰」是兩回事，不要混淆。

### 必做清單（依序執行）

> 四張表都齊了畫面才會出現；`VOC_SPEC` 是母集合，缺它其餘都沒用。

1. **`VOC_plant`**：新增該廠列，`isShow = 1`，並設好 `sort`（決定顯示順序）。
2. **`VOC_item`**：每個新項目新增一列（含 `itemid`、`item`、`unit`）。
   - 若項目名稱與既有廠區共用（例如同樣叫 `COD`），**沿用既有列即可**，不必重複新增。
3. **`VOC_SPEC`**：可經 `EditSPEC.aspx` 走簽核新增，或直接寫入。
4. **`VOC_SCADA_WEB`**：**必須先手動 INSERT 一列**（見下方「最大的坑」）。
5. **`VOC_Mail_List`**：要收異常派報信的話必須設定，否則不會發信。

## 三、⚠️ 最大的坑：QA 手測值是 UPDATE，沒有列就靜默失敗

不走 IH 的廠區，讀值要進來只有一條路：**`source = QA`（QA 手測值），
由人工在 `EditQA.aspx` 輸入**。

但 `UpdateQA()` 的寫入是 **UPDATE，不是 INSERT**（出處 `legacy/dbVOC.cs:2951`）：

```sql
Update [VOC].[dbo].[VOC_SCADA_WEB] Set rvalue=@rvalue, cdatetime=@cdatetime
Where plantno=@plantno And item=@item
```

**如果 `VOC_SCADA_WEB` 裡沒有這筆 `(plantno, item)`，這句 UPDATE 影響 0 列，
而且不會報任何錯誤**——畫面看起來存檔成功，實際上什麼都沒寫進去，
儀表板永遠是灰燈。

而新廠因為不走 IH，JOB 永遠不會替它建立 `VOC_SCADA_WEB` 的列。

> **所以務必先手動 INSERT 一列 `VOC_SCADA_WEB`（每個 plantno + item 一列），
> 之後 QA 手測值才寫得進去。** 初始值可設 `broken=0`、`rvalue` 留空。

## 四、其他會踩到的舊系統硬編碼

新廠區的項目**命名會直接影響行為**，這些都是舊系統寫死的：

### 1. 紅燈超標不一定會派報

`legacy/Job_dbVOC.cs:327`：

```csharp
bool bWater = (sItem.IndexOf("pH") > -1 || sItem.IndexOf("Cu") > -1 ||
               sItem.IndexOf("Ni") > -1 || sItem.IndexOf("SS") > -1 ||
               sItem.IndexOf("COD") > -1);
```

`bWater`（水質）與 VOC（空汙）之外的項目，**OOC/OOS 超標不會產生派報代碼**。
也就是說，新廠若有一個叫「氨氮」「總磷」之類、名稱不含上述五個關鍵字的水質項目，
**讀值超過 OOS 亮紅燈時不會發異常通知信**，而且沒有任何錯誤訊息。

> B 棧已用 `item.category` 修正此問題（2026-08-01，見 `docs/標準化與待調整清單.md` D7），
> 但**舊系統維持原樣**。臨時廠區上舊系統時必須注意這一點。

### 2. 溫度的雙邊規格只認 K21

`legacy/Job_dbVOC.cs:359`：

```csharp
if ((sItem.IndexOf("pH") < 0 && sItem != "溫度") || (sItem == "溫度" && sPlant != "K21"))
```

只有 **K21 的「溫度」**會被當成雙邊規格（`低-高`）處理，其他廠區的溫度一律視為單邊。
新廠若有溫度且需要上下限，舊系統**做不到**（需改程式）。

### 3. 項目名稱別名

`Home.aspx` 顯示時會做 `REPLACE(REPLACE(S.item,'COD2','COD'),'pH1','pH')`。
若新廠項目取名帶到 `COD2` / `pH1` 字樣，顯示時會被改寫，需留意。

## 五、自己寫 JOB 替代 IH（不走 Historian 的廠區）

不走 IH 的廠區，除了靠 `EditQA.aspx` 人工輸入外，**也可以自己寫一支小 JOB
直接寫 `VOC_SCADA_WEB` 與 `VOC_SCADA_HIST`**。這比人工維護乾淨，
角色等同 B 棧的 `services_b/sync_service.py`，等重構完成後即可退場。

### 5.1 兩張表與欄位對照

**`VOC_SCADA_WEB`（即時值，畫面直接讀這張）**

| 群組 | 欄位 |
|---|---|
| 定位鍵 | `plantno`, `item` |
| 讀值 | `rvalue`, `cdatetime`, `broken`, `light` |
| SCADA 管制值 | `OOS_HH`, `OOC_H`, `alert`, `OOS_LL`, `OOC_L`, `alert_L` |
| CWMS 管制值 | `OOS_HH1`, `OOC_H1`, `OOS_LL1`, `OOC_L1` |
| 雨水溝 | `TwentyFourHours` |

**`VOC_SCADA_HIST`（歷史值）**

欄位與 WEB 幾乎相同，但**多了 SPEC 門檻快照**，且**主鍵多一個 `cdatetime`**：

| 群組 | 欄位 | 說明 |
|---|---|---|
| **複合鍵** | `plantno`, `item`, **`cdatetime`** | 三個一起定位一列 |
| 讀值 | `rvalue`, `broken`, `light` | |
| SCADA 管制值 | `OOS_HH`, `OOC_H`, `alert`, `OOS_LL`, `OOC_L`, `alert_L` | |
| CWMS 管制值 | `OOS_HH1`, `OOC_H1`, `OOS_LL1`, `OOC_L1` | |
| **SPEC 門檻快照** | `OOS`, `OOC`, `alert1`, `recv` | **寫入當下的規格值** |
| 用途不明 | `closed` | 全檔 grep 不到任何使用，研判為遺留欄位 |

> **`alert` vs `alert1` 是兩回事**：`alert` 是 SCADA 端的管制值，
> `alert1` 是 SPEC 的 Alert 門檻——因為 `VOC_SPEC` 那一欄就叫 `alert`，
> 搬進同一張表會撞名，所以加了 `1`。
>
> **為什麼要存 SPEC 門檻快照**：門檻會被人修改。沒有快照的話，
> 回頭看歷史資料會用「現在的門檻」去解釋「當時的讀值」，結論會錯。
> B 棧的 `reading_history` 也是同樣設計。
>
> 注意 `VOC_SCADA_HIST` **沒有** `TwentyFourHours` 欄位——
> 雨水溝的 24 小時雨量不落地，是查詢時才 JOIN `PMS.dbo.Water_WindRainHistValue`。

### 5.2 ⚠️ `cdatetime` 必須無條件捨去到 15 分鐘整點

`legacy/Job_dbVOC.cs:117-120`：

```csharp
int m = dt1.Minute % 15;
string dt0 = dt1.AddMinutes(-m).ToString("yyyy/MM/dd HH:mm:00");
```

寫進 `VOC_SCADA_HIST` 的 `cdatetime` 一律對齊到 `:00 / :15 / :30 / :45`，秒數固定 `00`。

**這不是美觀問題——隔離功能靠這個對齊值去找歷史列**
（`legacy/Job_dbVOC.cs:134-136`）：

```sql
Update [VOC].[dbo].[VOC_SCADA_HIST] Set ... broken=2, light=3
Where plantno=@plantno And item=@item And cdatetime=@tdate   -- 精確等於對齊後的時間
```

若 JOB 寫入未對齊的時間戳（例如 `10:07:33`），**隔離核准後會找不到對應歷史列、蓋不掉**，
該筆歷史會留著真實讀值而非「保養中」，與舊系統行為不一致。

### 5.3 `light` 與 `broken` 的值域

`light`（對應舊版 int 變數，見 `services/dispatch_service.py:160`）：

| 值 | 意義 |
|---|---|
| 1 | 紅 |
| 2 | 黃 |
| 3 | 綠（**預設值**）|
| 4 | 橙 |

`broken`：`0`=正常、`1`=斷訊（JOB 寫）、`2`=保養中/隔離中（**Web 端寫**）。

> 隔離時舊系統寫的是 `broken=2, light=3`——`light=3` 是把燈號**重設回綠**
> （隔離中不該報警），真正代表「保養中」的是 `broken=2`。
>
> ★ 本專案的鐵則（CLAUDE.md 技術決策 #1）：**燈號一律從原始讀值重算，
> 不讀 DB 的 `light` 欄位**。JOB 寫 `light` 只是維持與舊系統的資料相容。

### 5.4 隔離覆寫的兩個特殊規則（你的 JOB 不用做，但不能被你蓋掉）

同一段程式碼（`legacy/Job_dbVOC.cs:101-108`）還揭露：

```csharp
if (item.IndexOf("雨水溝") < 0) { ...覆寫管制值... }   // 雨水溝項目不覆寫管制值
    OOS_HH = Iif(OOS_HH='-', '-', @status)             // 原本是 '-' 就保持 '-'
```

1. **雨水溝項目隔離時不覆寫管制值欄位。**
2. 覆寫時用 `Iif(欄位='-','-',@status)`——**原本標記為 `-`（未建置）的欄位保持 `-`**，
   不會被寫成「保養中」。

### 5.5 JOB 撰寫要點

```sql
-- 每 15 分鐘一輪；cdatetime 用對齊後的值
MERGE VOC_SCADA_HIST AS t
USING (SELECT @plantno AS plantno, @item AS item, @cdatetime AS cdatetime) AS s
   ON t.plantno = s.plantno AND t.item = s.item AND t.cdatetime = s.cdatetime
WHEN MATCHED AND (t.broken IS NULL OR t.broken <> 2) THEN   -- 別蓋掉隔離狀態
   UPDATE SET rvalue = @rvalue, broken = @broken, light = @light,
              OOS = @spec_oos, OOC = @spec_ooc, alert1 = @spec_alert, recv = @spec_recv
WHEN NOT MATCHED THEN
   INSERT (plantno, item, cdatetime, rvalue, broken, light, OOS, OOC, alert1, recv)
   VALUES (@plantno, @item, @cdatetime, @rvalue, @broken, @light,
           @spec_oos, @spec_ooc, @spec_alert, @spec_recv);
```

**五條要點**：

1. **`cdatetime` 對齊 15 分鐘**（最容易漏掉的一條，見 5.2）。
2. **`broken = 2` 的列不要動**——那是使用者核准的隔離，蓋掉會讓隔離期間照樣發異常信。
   `VOC_SCADA_WEB` 的更新同理，加上 `AND (broken IS NULL OR broken <> 2)`。
3. **用 UPSERT，不要單純 UPDATE**——這正是 `EditQA` 那個坑
   （UPDATE 影響 0 列不報錯，見第三節）。用 MERGE 就不必事先手動建初始列。
4. **`OOS`/`OOC`/`alert1`/`recv` 從 `VOC_SPEC` 當下的值抄過來**，這是快照的意義所在。
5. **SCADA/CWMS 那十個管制值欄位沒有來源時填 `-`**（不要填 0 或空字串）。
   填 `-` 舊系統會視為「未建置」而跳過比對；填數字會被拿去跟 SPEC 比對，
   不一致就亮**假橙燈**（提示「設定沒同步」）。

### 5.6 頻率

舊 JOB 的 `SCADA_VOC` 指令是**每 15 分鐘一輪**。畫面的資料過期判斷、
派報的節流邏輯都是照這個節奏設計的，自寫 JOB 建議對齊同樣間隔。
