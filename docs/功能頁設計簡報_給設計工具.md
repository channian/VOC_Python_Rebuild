# VOC 平台功能頁 — 視覺重新設計簡報

> 目的：交給設計工具（Claude Desktop 或任何設計協作）閱讀，用來重新設計儀表板旁邊的 11 個
> 功能頁（派送名單、規格維護、隔離申請、簽核管理、QA 手測、異常查詢、異常回覆、異常報表、
> 中水緊急通知、部門權限、ACL 使用者權限）。
> 這份文件只講「資料是什麼、規則不能改什麼、技術限制在哪」，**完全不限制版面/呈現方式**——
> 每頁最後都給了「獨立頁面 vs 維持彈窗」的建議，但這只是建議，設計端可以自行判斷。
> 設計完成後回這個 repo，我會負責把它接回 Jinja2 模板/獨立路由與後端資料。
> 建立日期：2026-07-11

## 〇、這是什麼系統、這批頁面是什麼（給設計者的背景）

工廠廢水/空污監測平台。首頁儀表板（已經改版完成，深色 SCADA 風格）負責「一眼看到異常」；
這 11 個頁面是儀表板旁邊的**工具/管理功能**——申請暫停監測、維護門檻設定、簽核、查歷史
異常紀錄、名單/權限維護等。使用者是廠務工程師與環安/簽核主管，操作頻率遠低於看儀表板
（多半是每天幾次、甚至每週幾次），所以這批頁面的體驗目標是「資訊清楚、操作不出錯」，
不是「一眼辨識」——與儀表板的設計目標不同，可以有不同的資訊密度與呈現節奏。

**目前的呈現方式**：全部 11 頁都是 Jinja2 partial 模板，透過 HTMX 抓回 HTML 片段塞進
`<dialog id="voc-modal">` 彈窗顯示，套用舊的亮色系（`static/css/voc.css`）。這次改版
**允許把內容多的頁面改成獨立頁面**（不必硬塞進 960px 寬的彈窗），內容單純的頁面也可以
繼續用彈窗——每頁最後一節都有這個建議，設計端可依內容判斷是否要提升為獨立頁面。

**新版深色設計系統**：儀表板已經套用了一套深色 SCADA 風格（`static/css/voc_b.css`，token
定義照抄自 `design_handoff_voc_platform/assets/colors_and_type.css`）。這批頁面重新設計時
**建議延用同一套視覺語言**（深色底、青色系強調、mono 字體用於數值/代號/時間戳），讓整個
平台視覺一致；但不是強制規定——如果設計端認為這批「管理/表單導向」的頁面適合不同的視覺
基調（例如更亮、更中性的辦公風格，方便長時間閱讀表格），也可以提出不同方案討論。

**使用情境**：桌面瀏覽器為主，不特別要求手機版。

## 一、共同技術基礎（11 頁皆適用的硬約束，設計時務必遵守）

### 1. 呈現機制與 API 慣例
- 目前：HTMX `hx-get` 抓 HTML 片段 → 塞進 `<dialog id="voc-modal">` → `showModal()` 開啟；
  關閉呼叫 `document.getElementById('voc-modal').close()`（**不是** Bootstrap Modal，全平台
  禁用 `data-bs-dismiss`）。
- 這次改版後，不論維持彈窗還是升級成獨立頁面，**下面列出的後端 API 路徑、request/response
  形狀、驗證規則都是硬約束，不能因為改版面而變動**——這些是既有後端契約，重新設計的是
  「怎麼呈現」，不是「後端怎麼運作」。
- 成功回應：`{"status": "success", "message": "<中文訊息>"}`（部分端點另帶 `formid` 等 id）。
- 業務規則錯誤：HTTP 400，`{"detail": "<中文錯誤字串>"}`（單一字串）。
- 欄位格式驗證錯誤：HTTP 422，`{"detail": [{"msg": "..."}, ...]}`（陣列，可能有多筆）。
  **錯誤訊息呈現區要能容納多行/多筆錯誤**，不是單行 toast 就能打發。
- 查詢類端點（GET）多半直接回傳陣列或物件，無 status 包裝。

### 2. 簽核狀態值（不可更動數值語意，兩處簽核共用同一組數字）
待簽核＝0、簽核中＝1、核准＝7、否決＝8、取消＝12（目前未使用）。

### 3. ⚠️ 重要現況落差：部分頁面的「規則文件」與「實際後端」不一致
`schemas/*.py` 裡有些檔案（`maillist_schema.py`、`dept_schema.py`、`acl_schema.py`、
`history_schema.py`）定義了完整驗證規則，但 **B 棧路由對「派送名單」「部門權限」「ACL」
「異常回覆」這 4 頁沒有套用這些 schema**，只做了型別檢查，沒有格式/邏輯驗證。也就是說
這 4 頁目前**送出去幾乎什麼都會被接受**（只有少數「找不到資料」「主鍵重複」會被擋）。

下面每一頁會標注「文件上定義、但目前未接線」的規則。設計上**建議還是把這些規則呈現在
UI 上**（例如手機號碼格式提示、必填標記），視為「這是本來就該有的行為」，不需要因為
後端還沒接線就不設計；未來補後端驗證時，UI 不用改。

相對地，**隔離申請、規格維護/送簽、QA 手測、簽核動作、中水通知**這 5 頁的驗證是真的
掛在後端生效的，這幾頁的規則文字可以直接視為「送出後一定會被檢查」。

### 4. 使用者身分現況
所有頁面的「操作者」目前是寫死的 mock 工號（Phase 3 才會接 LDAP 真實登入）。**不需要
設計「切換身分」之類的即時功能**，畫面上也不特別需要強調「目前登入者是誰」。

## 二、逐頁規格

### 頁面 1／11：派送名單維護

**用途**：維護異常 Email 派報的收件人與簽核人名單。一筆資料＝「某廠區 × 某報表類型 底下
某工號，是否收信、以什麼身分（TO主收件／CC副本）收信、是否為該廠區該類型的簽核人」。

**顯示欄位**

| 顯示欄名 | 型別 | 說明 |
|---|---|---|
| 廠區 plantno | str | 主鍵一部分 |
| 報表類型 rpttype | str | 主鍵一部分（如「水質異常」「水Alert」「水保養中」「空保養中」），同時是簽核用的分類 |
| 工號 empno | str | 主鍵一部分，可為群組/值班代稱 |
| 姓名 empname | str，可空 | |
| Notes ID notesid | str，可空 | 寄信時轉回 email |
| 方式 mailtype | 'TO'/'CC' | 建議用徽章區分，TO 用強調色 |
| Email mail | bool | 是否收信 |
| 簽核群組 signgrp | bool | 是否為該廠區該報表類型的簽核人 |

> 「手機」「簡訊」欄位是舊系統遺留、**B 棧資料層已經沒有這兩個欄位**，不建議在新設計中保留完整輸入區塊。

**輸入欄位（新增/編輯表單）**

| 欄位 | 型別 | 必填 | 說明 |
|---|---|---|---|
| 廠區 plantno | select | 是 | 編輯模式鎖定 |
| 報表類型 rpttype | select | 是 | 編輯模式鎖定 |
| 工號 empno | text | 是 | 輸入後自動帶出姓名/NotesID（`GET /maillist/employee/{empno}`） |
| 姓名 empname | text | 否 | 自動帶出，可手動覆蓋 |
| Notes ID notesid | text | 否 | 自動帶出，群組/值班工號需手填 |
| 派送方式 mailtype | select TO/CC | 是 | |
| 發 Email mail | select 1/0 | 是 | |
| 簽核群組 signgrp | select 1/0 | 是 | |

**後端 API**

| Method | 路徑 | Request | Response |
|---|---|---|---|
| GET | `/ui/maillist` | — | 渲染整頁 |
| GET | `/maillist/employee/{empno}` | path | `{empname, notesid, manual}` |
| POST | `/maillist/add` | `{plantno, rpttype, empno, empname?, notesid?, mailtype?="TO", mail?=true, signgrp?=false, remark?}` | `{status, message}` |
| POST | `/maillist/update` | 同上 + `{old_empno}` | 同上 |
| POST | `/maillist/delete` | `{plantno, rpttype, empno}` | 同上 |
| POST | `/maillist/toggle?enable=<bool>` | query | `{status, message, disabled}` |

**互動流程**：單純 CRUD（新增/編輯/刪除），無狀態機。另有一個**全域「暫停寄信」開關**——
切換後全平台所有派報 Email 停發，不分個別設定，需要視覺上明顯區分（高風險操作）。

**業務規則**
- 主鍵＝（廠區, 報表類型, 工號），重複會被拒絕。
- TO 嚴格綁該廠；CC 額外自動納入虛擬廠區（GMO／環工部）收件人，此邏輯背後發生，畫面不需呈現。
- 全域暫停旗標一啟用，**全部**派報信都不寄，不分個別 mail_on 設定。

**規模感**：廠區約 27 個，報表類型約 6～10 種，全表數百筆內，**不需要分頁**，但欄位偏多，
窄螢幕建議考慮收合或卡片式呈現。

**建議**：內容單純，**維持彈窗**即可；改版重點是拿掉已停用的手機/簡訊欄位、精簡排版。

### 頁面 2／11：規格維護

**用途**：維護每個「廠區 × 監測項目」的法規/管理門檻（法規許可值、OOS/OOC/Alert 三階
管制值），提供「直接編輯」與「送簽變更」兩種修改路徑。**這是 11 頁中複雜度最高的一頁。**

**顯示欄位（規格清單）**

| 顯示欄名 | 型別 | 說明 |
|---|---|---|
| 廠區 plantno | str | |
| 項目 item | str | 顯示名稱（內部別名 pH1→pH、COD2→COD 已轉換） |
| 來源 source/sourceid | str/int | 1=SCADA、2=CWMS、3=QA 手測 |
| 法規許可值 LAW | str | 單邊如 `"80"`，雙邊（pH/溫度）如 `"6-9"`，未設定顯示 `—` |
| OOS | str | 紅色語意 |
| OOC | str | 橙色語意 |
| Alert | str | 黃色語意 |

「我的申請單」「待簽核」頁籤另有：`formno`（申請單號）、`ftype_label`（新增/修改/刪除）、
`empstr`（申請人）、`cdatetime`（申請時間）、`fstatus`（狀態）／核准否決按鈕。

**輸入欄位**

*規格清單就地編輯*：來源（下拉）、LAW、OOS、OOC、Alert（4 個文字輸入）。

*送簽申請表單*：

| 欄位 | 型別 | 必填 | 說明 |
|---|---|---|---|
| 類別 ftype | select I/M/D | 是 | 新增/修改/刪除 |
| 廠區 plantno | text（建議 datalist） | 是 | |
| 項目 item | text（建議 datalist） | 是 | |
| 來源 source_id | select | 是 | |
| 法規許可值/OOS/OOC/Alert | text | 否 | 見下方格式規則 |
| 備註 remark | text | 否 | |

**欄位格式驗證（真正生效於後端）**
- 空字串或 `"N/A"` 視為未設定，合法。
- **pH 項目必須雙邊**（`"6-9"`），**非 pH 項目必須單邊**（`"80"`），格式不符直接拒絕。
- 每段最多小數點後 2 位；雙邊時下限不可大於等於上限。
- **OOC/Alert 層遞防呆**：單邊時 OOC 上限須大於 Alert；雙邊時 OOC 範圍須比 Alert 範圍寬。
  ⚠️ 這條雙邊方向判斷是團隊依直覺補上的規則，舊系統原始邏輯疑似從未真正上線過，**待業務
  確認正確方向**——UI 上錯誤訊息文案需要保留，但底層邏輯未來可能調整。

**後端 API**

| Method | 路徑 | Request | Response |
|---|---|---|---|
| GET | `/ui/spec` | — | 渲染整頁 |
| GET | `/spec/list?plantno=&item=` | query | 規格陣列 |
| POST | `/spec/create` | `{plantno, item, LAW, OOS, OOC, alert, source_id, remark?}` | `{status, message}` |
| POST | `/spec/update` | 同上 | 同上 |
| DELETE | `/spec/delete?plantno=&item=&remark=` | query | 同上 |
| POST | `/spec/apply` | 同上欄位 + `{ftype: 'I'/'M'/'D'}` | `{status, message, formid}` |
| GET | `/spec/applies?plantno=&item=` | query | 申請單陣列 |
| GET | `/spec/todos` | — | 待簽核清單 |
| POST | `/spec/sign` | `{formid, flowid, actionid, comment?}` | `{status, message}` |

**互動流程**

*A. 直接編輯*：點編輯 → 改欄位 → 儲存 → `POST /spec/update` → **立即生效，無需簽核**。

*B. 送簽變更*：
```
填表單 → POST /spec/apply → 建立申請單，fstatus=待簽核(0)
→ 出現在「待簽核」頁籤 → 簽核人核准(1)/否決(9) → POST /spec/sign
  → 核准：套用回規格主表，fstatus=核准(7)
  → 否決：僅改狀態，fstatus=否決(8)
```
⚠️ **已知功能缺口**：這條送簽路徑目前**沒有真正建立簽核流程/指派簽核人**，`/spec/sign`
也**沒有身分檢查**（不像隔離簽核會驗證是不是你這關）。也就是說「待簽核」頁籤目前對任何
打開這頁的人都可見、都可操作。設計不需要為此特別做角色區分 UI，但若要做，應預留位置。

**業務規則**
- 就地編輯（立即生效）與送簽申請（需簽核）是兩種不同權限強度，但**目前後端沒有角色檢查
  區分誰能用哪一種**——這是可以在文件說明的業務語意落差，但系統尚未實作。
- 同廠區/項目若已有「待簽核」或「簽核中」的申請，禁止重複送出。
- 刪除規格會連帶清除該項目**目前的**讀值（因外鍵限制），但歷史讀值不受影響——刪除確認
  文案建議提示這點。

**規模感**：27 廠區 × 平均 5～10 項目，規格主表約 150～250 筆；送簽/待簽核通常個位數到
十幾筆。**不需要分頁**，但建議提供廠區/項目篩選（目前只有前端建議值，無真正篩選）。

**建議**：**升級成獨立頁面**。4 個頁籤（清單/送簽/我的申請/待簽核）、就地編輯、多欄位
格式驗證、雙軌流程，塞進彈窗資訊密度過高；待簽核頁籤未來也可能需要更完整的審核介面
（異動前後對比等）。

### 頁面 3／11：隔離申請

**用途**：申請「暫停監測」某廠區某項目一段時間（如儀器校正），需簽核核准才生效；核准
期間該項目不計入異常判定與派報。

**顯示欄位（目前有效隔離）**

| 顯示欄名 | 型別 | 說明 |
|---|---|---|
| 申請單號 ccno | str | `yyyyMMddNNN`，當日流水 |
| 廠區 plantno | str | |
| 申請人 empstr | str | `工號-姓名` |
| 原因 mdfdesc | str | |
| 開始/結束時間 stime/etime | datetime | |
| 備註 remark | str，可空 | |

僅列出已核准且目前時間落在區間內、未刪除的紀錄（即時查詢）。

**輸入欄位**

*新增申請*：

| 欄位 | 型別 | 必填 | 驗證規則 |
|---|---|---|---|
| 廠區 | select | 是 | 選擇後動態載入該廠可隔離項目 checkbox |
| 開始時間 stime | datetime-local | 是 | 不可小於系統目前時間 |
| 結束時間 etime | datetime-local | 是 | 不可小於開始時間；**(etime−stime) 不得超過 1 小時** |
| 隔離項目 items[] | checkbox 群組 | 是（至少 1 個） | |
| 隔離原因 mdfdesc | text | 是 | |
| 備註 remark | text | 否 | |

*修改申請*：同上規則 + 針對已核准且未過期的原單建立新單（非原地修改）。

*隔離時間修改*（僅限特定權限角色）：

| 欄位 | 型別 | 必填 | 驗證規則 |
|---|---|---|---|
| 新結束時間 etime | datetime-local | 是 | 不可小於原結束時間（只能延長），**不受 1 小時上限限制**（例外通道） |
| 備註 remark | text | 否 | |

**後端 API**

| Method | 路徑 | Request | Response |
|---|---|---|---|
| GET | `/ui/control` | — | 渲染整頁 |
| GET | `/ui/control/items?plantno=` | query | HTMX 局部：該廠可隔離項目 |
| POST | `/control/create?is_commit=true` | `ControlCreate` | `{status, message}` |
| POST | `/control/submit/{ccid}` | path | 同上 |
| POST | `/control/modify?is_commit=true` | `ControlModify` | 同上 |
| POST | `/control/time` | `ControlTimeUpdate` | 同上；無權限回 403 |
| GET | `/control/my_apply?plantid=&statusid=&ccid=` | query | 我的申請單列表 |
| GET | `/control/tags/{ccid}` | path | 該單明細項目 |

**互動流程**

```
填表單送出 → POST /control/create → fstatus=待簽核(0)
  → 立即建立簽核流程（找該廠區的簽核人）→ fstatus=簽核中(1) → 寄「待簽核」通知信
  → 簽核人核准(7)/否決(8) → 任一人動作即結案（單關卡 OR 邏輯，非全員會簽）
  → 寄「核准/否決」通知信給申請人
```

**業務規則**
- **隔離時間上限一律 1 小時**，不分項目種類。
- 重複申請防呆：同（廠區, 項目, 來源）在時間區間**重疊**即擋下（⚠️ 與舊系統「只擋完全相等」
  行為不同，較嚴格，待業務確認何者正確）。
- 簽核人＝該廠區對應分類（VOC 項目歸「空保養中」，其餘歸「水保養中」）底下登記的簽核人，
  **排除申請人自己**、排除離職員工。若無簽核人，送簽直接失敗。
- 簽核為**單關卡 OR 邏輯**：任一人核准或否決，流程立即結案。
- 「隔離時間修改」是**唯一不走簽核**的例外通道，僅限特定權限角色，只能延長不能縮短，也
  不受 1 小時上限限制——舊系統遺留的特權後門，上線前建議業務評估是否合理。
- 核准後**不竄改讀值**：隔離狀態由查詢時即時判斷，不會覆寫顯示值。

**規模感**：目前有效隔離通常個位數到十幾筆（1 小時上限使然）。**不需要分頁**。

**建議**：內容中等（清單 + 3 種表單），操作聚焦單一廠區當下狀態，**可維持彈窗**，但目前
3 段表單同時存在（用顯示/隱藏切換）建議改成更清楚的分頁籤或抽屜式切換。

### 頁面 4／11：簽核管理

**用途**：顯示目前登入者「待簽核」的**隔離申請單**清單，供核准或否決。

> ⚠️ 這頁只處理**隔離申請**的簽核，不含規格維護送簽（規格的待簽核在規格維護頁的「待簽核」
> 頁籤，走不同資料表）。兩者概念相似但資料/入口完全分離，不建議合併成「統一簽核中心」
> 除非同時調整後端資料模型。

**顯示欄位**

| 顯示欄名 | 型別 | 說明 |
|---|---|---|
| 申請單號 ccno | str | |
| 廠區 plantno | str | |
| 申請人 empstr | str | |
| 類型 ttype | str | 新增／修改隔離區間 |
| 原因 mdfdesc | str | |

**輸入欄位**：無表單，僅核准／退回兩顆按鈕。目前「退回」不要求輸入原因（傳空字串）——
與規格維護「待簽核」的否決會要求輸入原因不一致，**設計上可以視為統一機會**（一律要求
填否決原因），後端欄位本身是選填、加上此要求不影響契約。

**後端 API**

| Method | 路徑 | Request | Response |
|---|---|---|---|

數字系統，容易混淆，UI 文案不需要暴露這些數字，但開發溝通時要分清楚。

**互動流程**
```
查目前登入者尚未簽核、所屬單仍在簽核中的隔離單 → 逐筆顯示核准/退回
→ POST /flow/sign → 核准/否決 → 任一人動作後立即結案，該單從所有簽核人待辦清單消失
→ 寄送核准/否決通知信給申請人
```

**業務規則**
- 簽核人不可為申請人本人（在「找簽核人」那一步就排除，不是簽核當下才檢查）。
- 只有一關（單階群組簽核），**不需要**「簽核關卡進度」這種多階視覺元件。
- 查無簽核資格會報「您不具備簽核資格，或此關卡已完成簽核」——這句話同時涵蓋「真的沒資格」
  與「已經簽過」兩種情況，無法從錯誤內容區分。

**規模感**：待簽核通常個位數到十幾筆。**不需要分頁**。

**建議**：內容單純，**維持彈窗**。

### 頁面 6／11：異常查詢

**用途**：依日期區間／廠區／項目查詢歷史異常派報紀錄（含是否已回覆原因）。純查詢，不可編輯。

**業務規則**
- 查詢母體 = 派報紀錄 ⋈ 派報明細（一封信可能含多個項目，每個項目一列）。

查詢可能一次撈回數千筆。**建議**：把預設區間（本月 1 日～今天）視為硬性建議，結果表格
加上分頁或虛擬捲動。

**建議**：內容單純（篩選+一張表），但資料量會成長、且與「異常回覆」高度相似，**建議維持
彈窗**，重點放在表格分頁/捲動處理，不需要升級成獨立頁面。

### 頁面 7／11：異常回覆

**用途**：與「異常查詢」共用完全相同的查詢邏輯與資料來源，額外提供「針對某筆異常紀錄

**顯示欄位**：與「異常查詢」完全相同，多一欄「操作」（每列一顆「回覆」按鈕）。

**輸入欄位**

*篩選表單*：與「異常查詢」完全相同。

*原因回覆（行內展開編輯）*：

| 欄位 | 型別 | 必填 | 說明 |
|---|---|---|---|
| 原因說明 reason | textarea | ⚠️見下 | 文件定義「不可空白」，但**目前 B 棧路由未套用此驗證**，前端也未擋空白——目前空白原因會被接受存檔。UI 上可呈現必填提示，但需理解目前不是真正強制。 |

**後端 API**

| Method | 路徑 | Request | Response |
|---|---|---|---|
| GET | `/ui/reason?plant=&item=&sdate=&edate=&mt=` | query | 渲染整頁（邏輯同 `/ui/history`） |

**互動流程**

- 與「異常查詢」同一份底層資料、同一組查詢 API，視覺語言應盡量一致。

**規模感**：同「異常查詢」，需考慮分頁/長列表。

**建議**：**維持彈窗**，理由同異常查詢；若異常查詢升級成獨立頁面，這頁應同步升級（兩者
共用度高，拆開會增加維護負擔）。

### 頁面 8／11：異常報表

**用途**：對指定廠區/項目/日期區間的異常派報紀錄做**線上統計**（長條圖、交叉表、排行榜），

**顯示欄位**

*排行表*：`rank`（並列不跳號）、`plantno`、`count`；前 3 名/後 3 名建議顏色區分，可點擊下鑽。

**輸入欄位**：篩選表單，與「異常查詢」完全相同。**本頁無任何寫入型輸入欄位**，純統計呈現。

**後端 API**

| Method | 路徑 | Request | Response |
|---|---|---|---|
| GET | `/report/ui?plant=&item=&sdate=&edate=&mt=` | query | 渲染整頁 |
| GET | `/report/logs?plant=&item=&sdate=&edate=&mt=` | query | `{sdate, edate, rows, summary:[{plantno,count,pct}], pivot:{columns,rows}, ranking:{rows:[{rank,plantno,count}], max_rank}}` |

**互動流程**：篩選→統計呈現，無編輯、無狀態機。三種統計視圖**同時**顯示（非頁籤切換），
下鑽會切換整個彈窗內容成「異常查詢」頁。

**業務規則**
- ⚠️ **統計母集合與舊系統有落差**：舊系統統計刻意不含雨水溝項目，B 棧目前**含**雨水溝，
  統計數字會比舊系統多。這是已知落差，若設計要呈現「與歷史數據對照」的說明文字需註明。
- 排行榜採**並列名次**（如兩廠並列第 1，下一名直接是第 2），設計名次視覺時需考慮並列情況。

**規模感**：輸出是聚合後的統計（依廠區/項目分組），實際顯示列數遠小於明細筆數——長條圖
最多約 27 列、交叉表最多約 10×27 格、排行榜最多約 27 列，**這幾個視圖本身不需要分頁**，
但查詢區間很大時後端運算可能較慢（效能考量，非畫面設計考量）。

**建議**：**升級成獨立頁面**。三種統計視圖同時呈現、內容密度高，且是管理階層常用的決策
參考頁，值得比照 BI 儀表板給更大呈現空間（加大交叉表可視區域、加入圖表互動）。

**建議**：內容單純，**維持彈窗**，但因為是「會實際寄送 Email 給外部收件人」的高風險操作，
建議加強確認流程的視覺嚴肅感（目前只有瀏覽器原生確認框，可考慮升級成頁內確認卡片）。

- 主鍵＝（廠區, 部門代碼），重複會被拒絕。
- `plantid=29`＝「全廠」，是沿用舊系統的固定值，非資料驅動的正式標記——只需知道它會出現
  在廠區下拉裡，行為與一般廠區一致，不需特殊 UI 區分，文字標註即可。
- **部門名稱目前沒有真正的中文名稱來源**：系統是用「該部門代碼是否存在至少一位在職員工」
  來判斷代碼有效，有效就直接把**部門代碼本身**當顯示名稱回傳。也就是「部門名稱」欄位
  實質上幾乎必然等於部門代碼，不需要為它設計太多視覺權重，也不用預期會顯示人類可讀全名。

**規模感**：27 廠區（含全廠），每廠通常個位數到十幾個部門，全表約數十到一兩百筆。
**不需要分頁**。

**建議**：內容單純，**維持彈窗**。

### 頁面 11／11：ACL 使用者權限

**用途**：維護「隔離維護」「隔離查詢」這兩種角色的權限名單（誰在哪個廠區具備哪種角色）。

> 這頁目前**只掛在舊版介面**，尚未出現在新版儀表板工具選單裡——這次改版除了頁面本身，
> 也需要決定它在新介面的入口位置（可考慮歸類到「系統管理」區）。

**顯示欄位**

| 顯示欄名 | 型別 | 說明 |
|---|---|---|
| 廠區 plantno | str | |
| 角色 roletype | str | 角色名稱文字（如「隔離維護」「隔離查詢」） |
| 工號 empno | str | |
| 姓名 empname | str，可空 | |
| Notes ID notesid | str，可空 | |
| 水/空區分 stype | str | DB 存 空/水/ALL，畫面 ALL 顯示「全區」 |

篩選：廠區（select，動態載入）、角色（select，動態載入）、工號（text）。

**輸入欄位**

| 欄位 | 型別 | 必填 | 說明 |
|---|---|---|---|
| 廠區 plantno | select | 是 | 編輯模式鎖定 |
| 角色 role_id | select | 是 | 編輯模式鎖定；**下拉只列出隔離維護與隔離查詢兩種角色** |
| 工號 empno | text | 是 | 自動帶出姓名/NotesID |
| 姓名/Notes ID | text，唯讀 | — | 自動帶出 |
| 水/空區分 stype | select（空/水/全區） | 是 | 預設「全區」 |
| 備註 remark | text | 否 | |

⚠️ **重要落差**：文件定義「角色只能是這兩種」，但**目前後端沒有真正檢查**——唯一擋住其他
角色的地方是前端下拉選單只顯示這兩個選項。若有人直接呼叫 API 帶其他角色，系統目前不會擋。
這不影響畫面呈現（下拉本來就該只列這兩種），但屬於需要標注的技術現況。

**後端 API**

| Method | 路徑 | Request | Response |
|---|---|---|---|
| GET | `/ui/acl` | — | 渲染整頁外殼（資料由前端另外 fetch，見下方互動流程） |
| GET | `/acl/list?plantno=&roletype=&empno=` | query | 名單陣列 |
| GET | `/acl/roles` | — | 角色清單（固定回 2 筆） |
| GET | `/acl/plants` | — | 廠區清單 |
| GET | `/acl/employee/{empno}` | path | `{empname, notesid}` |
| POST | `/acl/create` | `{plantno, role_id, empno, stype?='3', remark?}` | `{status, message}` |
| POST | `/acl/update` | 同上 + `{old_empno, old_stype?}` | 同上 |
| POST | `/acl/delete` | `{plantno, role_id, empno}` | 同上 |

**互動流程**
```
開啟頁面（回傳空殼）→ 前端立即並行 fetch 廠區/角色/名單三支 API → 組出下拉與表格
```
這是 11 頁中**唯一**採「先渲染空殼、資料完全由前端二次請求」模式的頁面，其餘都是伺服器
渲染時直接把資料塞進 HTML。改版時可決定維持這種模式或改成與其他頁一致的伺服器渲染。

**業務規則**
- 主鍵＝（角色, 廠區, 工號），重複會被拒絕。
- 目前只管理 12 種角色中的 2 種，其餘角色舊系統本身也沒有網頁介面，不是本次改版要解決
  的範圍，文案上誠實標注「僅開放這兩種角色管理」即可。
- 此權限名單**目前尚未真正掛到各功能頁做守門**（只有「隔離時間修改」一個端點有真正檢查）
  ——設定了某工號沒有權限，目前系統不會真的擋住他操作。對畫面設計沒有直接影響，但若要
  強調「這是權限控管核心頁」，需留意目前實際效力有限，屬系統過渡期現況。

**規模感**：2 種角色 × 27 廠區 × 每廠每角色通常個位數人員，全表約數十到百餘筆。**不需要
分頁**。

**建議**：資料量與操作複雜度接近「部門權限」「派送名單」，基礎上**可維持彈窗**；但若設計
端打算把「系統管理」相關功能（ACL、未來的廠區/項目管理等）集中規劃成獨立的「系統管理」
區塊，**建議把 ACL 一併規劃為獨立頁面**，與其他系統管理功能並列，而非單獨留在工具彈窗裡。

## 四、設計系統延用參考

新版儀表板的設計 token 定義在 `static/css/voc_b.css`（照抄自
`design_handoff_voc_platform/assets/colors_and_type.css`），重點：
- 深色堆疊：`--bg-0`～`--bg-4`（由淺至深的背景層次）
- 強調色：`--accent`（青色，focus/連結）、`--blue`（主要按鈕）
- 狀態色：`--ok`/`--warn`/`--err`/`--info`/`--muted`，各有 10% 透明背景版與發光版
- 字體：Sans 用 Inter，數值/代號/時間戳一律用 JetBrains Mono
- 間距基準 4px；圓角：卡片 10–14px、按鈕/輸入框 6px、狀態 pill 999px
- 目前彈窗版有一份過渡期蓋版 CSS（`static/css/voc_b_modal_dark.css`），如果重新設計這批
  頁面，**不需要延用這份蓋版手法**，可以直接採用 `voc_b.css` 的 token 從頭設計。

這批頁面是否要 100% 沿用儀表板配色，或是設計一套「管理頁專屬、更中性/更適合長時間閱讀
表格」的變體配色，交由設計端判斷——這不是硬約束，只是提供現有系統的視覺基準供參考。
