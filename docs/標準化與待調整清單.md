# 重構過程發現的不合理項目與標準化建議（與環工部討論用）

> 2026-07-11 彙整。來源：Phase 1 legacy 精讀、Phase A Schema B 重構、A→B 搬遷實測、
> V2 UI 改版全程發現。分四類：
> **A＝已在 B 棧標準化（請環工部認可新做法）**、**B＝資料清理（正式搬遷前必做）**、
> **C＝業務規則待確認（規則本身要環工部拍板）**、**D＝權限與流程（等 AD 串接後接上）**。
> 每項標注出處，細節可回查對應文件/程式註解。

## A. 已在 B 棧標準化——請環工部「認可新做法」（新資料建置也照此標準）

| # | 舊系統做法（不合理處） | B 棧新做法 | 討論點 |
|---|---|---|---|
| A1 | **隔離竄改讀值**：隔離核准後直接把 rvalue/管制值覆寫成「保養中」字樣，原始讀值永久遺失 | 讀值照實記錄，保養狀態由隔離單有效區間即時 JOIN 推導，永不覆寫 | 認可即可。注意：舊系統歷史資料已被污染救不回，搬遷時這些區間讀值會標為 maintenance |
| A2 | **讀值混型字串**：rvalue 一欄混存數字/'N.D'/'<0.05'/'斷訊'/'保養中'，每次用都要拆字串猜型別 | 拆成 value(數值)+status(狀態碼)+raw_text(原文備查) 三欄 | 認可即可。新資料建置（QA 輸入、JOB 轉拋）一律照此格式 |
| A3 | **門檻存字串**：'6-9'/'80'/'-'/'建置中' 混存一欄，計算前都要 parse | 拆 low/high 數值 + status(valid/na/building) | 認可即可 |
| A4 | **派報紀錄用字串比對**：msg1/msg2 長字串 LIKE 比對決定首發/再發 | mail_log(信件)+mail_log_item(逐項目+條件碼)正規化 | 認可即可 |
| A5 | **plantid=29 魔法數字**代表「全廠」，程式到處寫死判斷 | plant.kind 欄位（normal/virtual_group/all）明確表達 | 認可即可；新廠區清單請直接標 kind |
| A6 | **歷史讀值無門檻快照**：異常回溯時查不到「當時的管制值是多少」 | reading_history 每筆快照當下 SPEC 門檻（稽核需求，已依你先前要求設計） | 認可即可 |
| A7 | **簡訊/手機欄位**：功能早已停用，欄位一直留著 | B 棧不建這些欄位，新 UI 不顯示 | 認可即可 |
| A8 | 舊 JOB 用「tag 順序相符」逐筆比對，順序一亂就**靜默漏同步**（pH 改名事件根因） | tag_mapping 表明確驅動，每筆對不上都記入 errors 不靜默 | 認可即可；tag 對應表就是你要跟環工部確認的「新資料建置需求」第 4 張表 |

## 建議的下一步順序（對應使用者 2026-07-11 提案）

1. **你（使用者）→ 環工部**：帶本文件 C 類（拍板）＋ B 類（資料清理）＋「新資料建置需求」
   4 張表去談。談完的結論回填給主控。
2. **平行進行：AD/LDAP 串接**（使用者提案 1，同意）——這是 D 類全部項目的前置，
   也是「派報/簽核用真人測試」的前置。依 docs/ad_integration_guide.md 實作
   auth_service LDAP 驗證＋session＋current_user 全面取代 MOCK_USER，然後依序接
   D1（守門）→ D2（規格簽核補流程）→ D3/D4。D5 不依賴 AD，可先做。
3. **新 JOB 讀取實際資料**（使用者提案 2，同意）——等環工部給 tag 對應表
   （新資料建置需求第 4 張）後，把 tag_mapping 從 kepware_sim 模擬表換成真 A 端轉拋庫，
   run_sync_worker 對真資料試跑（Track 1 的 write_legacy_sink 也在此階段實測）。
