## 四、執行順序建議（兩波）

- **第 1 波（3 包平行）**：WP-E、WP-F、WP-A —— 兩個獨立頁價值最高（規格維護是使用者
  最近實測的痛點頁、異常報表是管理決策頁），殼（WP-A）先定案讓工具選單/連結結構穩定。
  第 1 波收線驗收後 commit（此時舊 partials 照常運作，平台不會壞）。
- **第 2 波（3 包平行）**：WP-B、WP-C、WP-D —— 8 個 modal 全換深色原生版。收線時
  router 一次切換＋刪蓋版 CSS。
- 理由：一次發 6 包主控驗收吞吐會塞車；兩波各自可獨立上線、風險小；且第 2 波可吃到
  第 1 波驗收時發現的共通問題（toast 形狀、錯誤訊息呈現慣例）修正後的經驗。

## 五、風險與注意

1. V2 設計稿的互動是**前端假資料**（React 式 state），agent 必須改接真 API——簡報文件
   裡每頁的「後端 API 契約」就是唯一標準；422 錯誤是陣列要 join 顯示。
2. 異常查詢/回覆合併後，`/ui/history` 與 `/ui/reason` 兩個 URL 都保留（同模板、mode 參數
   不同），避免既有測試與工具選單斷鏈。
3. 規格維護「待簽核」的簽核流程缺口（無真正簽核人指派/身分檢查）是**既知後端缺口**，
   本輪只做 UI，不修後端；設計稿的落差提示條要保留。
4. 派送名單「全域暫停寄信」是高風險操作，V2 有專屬警示區塊——實作時 `/maillist/toggle`
   的 enable 語意要跟後端對一次（enable=true 是「啟用寄信」還是「啟用暫停」，接線時主控驗證）。
5. Windows/內網環境：Google Fonts link 保留但 fallback 必須完整（voc_b.css 已處理）。
