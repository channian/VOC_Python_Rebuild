# 給環工部：申請異動 Tag 前要知道的事

> 這份文件不談程式碼，只用白話說明「為什麼改一個 tag，畫面上一堆項目會跟著跳異常」，
> 以及申請廠區異動 tag 時該注意什麼。技術細節（給工程師看的）在 `docs/legacy_source_analysis.md`
> 「SCADA Tag 對應機制完整還原」章節。

## 一句話總結

**系統每 15 分鐘會去現場「按名字」抓一次資料，如果 tag 改名沒有同步告訴系統，
系統會卡住、停在舊資料不動，而且會連帶拖累「後面排隊」的其他項目，讓一堆看起來不相關的
監測項目一起跳橙燈、紅燈或顯示斷訊——但那些項目其實沒有真的異常，只是資料沒更新到而已。**

## 用一個比喻理解

把每個監測項目（例如 K12 的 pH）想像成一張「資料卡」，卡片上有好幾格要填：

- 「目前讀值」
- 「異常上限（OOS）」
- 「警戒上限（OOC）」
- 「提醒上限（Alert）」
- （像 pH 這種項目還多兩格：「異常下限」「警戒下限」）

每一格背後，都對應現場一個「感測器訊號的名字」（就是 tag，可以想成貼在感測器上的一張條碼標籤）。
系統每 15 分鐘會去現場**照著登記的名字**掃一輪所有標籤，把讀到的數字一個一個填回資料卡對應的格子。

**問題在於**：這個「填回去」的動作，是**照順序一個蘿蔔一個坑對**，不是「看到名字就直接精準對應」。
如果現場把某個標籤換了個新名字（例如廠區申請把感測器的訊號名稱改掉），但系統裡登記的名字
沒有跟著同步更新，這個「照順序對」的動作在改名的那個點就會**卡住、對不上**。而且一旦卡住：

- **這一輪**該站主機底下，**排在卡住點後面的所有 tag，全部都不會被更新**，
  資料卡上的格子維持上一輪的舊數字不動。
- 系統**不會主動跳出來告訴任何人**「哪個標籤對不上」——它就是安安靜靜地卡住，什麼訊息都不發。
- 舊數字跟現在的規格設定兜不起來，系統就會誤判成「異常」，亮橙燈、紅燈，或顯示「斷訊」。
- 這個狀況會**每 15 分鐘重複發生**，一直到把名字改回一致為止，不會自己好。

所以您可能會看到：明明只改了一個 tag，結果某個廠區一整排完全不相干的項目全部跳異常——
那不是真的水質出問題，是系統「卡住沒更新」被誤判。

## 例子

**例子 1：一般水質項目（例如 COD）只需要一個標籤**
COD 只有「上限」需要顧，所以只登記一個 tag（「異常上限」那一格）。您如果發現某個項目的
「下限」欄位一直是空的，**這是正常的**，不是漏設定，因為系統本來就只看上限有沒有超標。

**例子 2：pH 需要兩個標籤，系統會把兩個數字拼成一組**
pH 太高太低都不行，所以「異常上限」跟「異常下限」各自對應一個**獨立**的 tag。
系統抓到兩個數字後，會把它們拼成一個字串顯示（例如 `6.5-8.5`）。這就是您在資料庫裡
看到「一個門檻值好像是兩個 tag 組合起來」的真相——**背後真的是兩筆各自獨立的設定，
一筆管上限、一筆管下限，系統把兩者的值黏在一起顯示**。

**例子 3：改名沒同步，一片遭殃**
假設廠區把 K12 的「pH 下限」那個標籤，從舊名稱 `K12.PH.LL` 改成新名稱 `K12_PH_LOW`，
但只在現場設備上改了名字，沒有同時請 IT 把系統裡登記的名字也改成一致。結果：
- K12 的 pH 下限本身當然對不上、拿不到新資料。
- **同一台主機底下，排在 pH 下限「後面」登記的所有其他項目**，這一輪也全部拿不到新資料，
  一起卡在舊數字，一起被誤判成異常。
- 隔天、隔週，只要沒人發現去改回一致，天天都會重複發生同樣的異常。

## 申請 tag 異動時，請務必確認

1. **廠區端改 tag 名稱、新增/移除量測點時，必須同步通知 IT／系統維護人員，
   把系統裡登記的名字改成跟現場完全一致**（連大小寫、底線、空白都要一模一樣，
   差一個字元就會對不上）。
2. **如果是 pH 或溫度這種需要「上限＋下限」的項目**，新增 tag 時要記得**兩個都要新增、
   兩個名字都要跟現場一致**，只改其中一個一樣會出問題。
3. **改完之後不會有系統跳出來提醒您改對還是改錯**——請主動請 IT 人員在改完後確認一次，
   看看該廠區的項目有沒有恢復正常更新（不再停在改動當下的舊數字），而不是等使用者
   反映異常才發現。
4. 如果發現某個廠區突然一整排項目一起跳橙燈/紅燈/斷訊，**先懷疑是不是最近有 tag 異動**，
   再去現場確認水質——很多時候不是真的水質異常，是系統資料沒更新到。

## 這是舊系統的已知限制，新系統已經修正

上面說的「照順序對、對不上就整批卡住、也不會通知任何人」是**舊系統**的既有設計缺陷。
正在建置中的新系統（PostgreSQL / Schema B）已經改用「一筆一筆獨立比對」的做法，
單一 tag 對不上只會記錄成一筆待處理紀錄，**不會連累其他項目、也不會靜默吞掉**。
但在新系統正式取代舊系統之前，舊系統這個限制依然存在，異動 tag 時仍要照上面的 SOP 小心操作。
